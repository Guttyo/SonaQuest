# dev-log

1つのテーマ（PR、調査、設計の変更、Phaseの区切り）について、経緯・理由・教訓を `docs/dev-logs/` に1ファイルで残す。書く条件・ファイル名・ほかの記録との違いは `docs/dev-logs/README.md` を正とする。ユーザー設定の `create-dev-log` エージェントは使わない。

## 1. 書く前に
- `docs/dev-logs/README.md` を読み、「いつ書くか」に当てはまるか、同じテーマの記録が既にないかを確かめる。既にあれば新しく作らず、追記するかをオーナーに聞く。
- 対象（Issue・PR・ブランチ・コミットの範囲）を決める。決められないときはオーナーに聞く。

## 2. 事実を確かめる（いちばん大事）
記憶・推測・要約から書かない。確かめた結果だけを書く。
- 引用するファイルは、書く前にすべて Read で開く。ファイル名・関数名・ADR番号を記憶や推測で書かない。
- 変更したファイルの一覧は `git log --stat` や `git show --stat <コミット>` の結果から写す。関係がありそうでも差分に無いファイルは足さない。
- コミットは `git log --oneline` で確かめる。SHAを作らない。
- PRとレビューの指摘は `gh pr view <番号> --comments` で確かめてから書く。PR番号を作らない。
- KEEP-THINKING・STATUS・PR本文の要約から書き起こさない。要約にある主張を使うときは、元の記録（コミット、指摘、試験の結果）で裏付けられるかを確かめ、裏付けられなければ「推測」に置く。
- コードを引用するときは、実際のコミットにある行だけを載せる（`git show <コミット>:<パス>` で確かめる）。確かめられないなら、コードを載せずに文で書く。
- 確かめられない情報が要るときは、書かずにオーナーに聞く。

## 3. 本文の構成
当てはまらない見出しは省く。空の見出しを残さない。

- 冒頭：日付、対象（Issue・PR・ブランチ・主なコミット）、関係するADR
- 背景：なぜこの作業が要ったか（差分を見ても分からないこと）
- やったこと
- レビューの経過（レビューが2回以上のとき）：回・主な指摘・対応 の表
- つまずいたことと教訓：「次に同じ場面でどうするか」の形で書く。具体的なコミット・ファイル・指摘に結びつける。一般論は書かない
- 確かめたこと：試験の名前と結果、確かめた日付と環境（OS、Python等の版）。動かしていないものを「確認済み」と書かない（CLAUDE.md 絶対ルール10）
- 推測：確かめていないが、こう考えたこと。確かめたことと混ぜない
- 残ること：Issue番号で書く。Issueが無いものは、立てるかをオーナーに聞く（自分で立てない）

## 4. 書いてはいけないこと
- CLAUDE.md 絶対ルール8の情報：制作者の勤務先とそれを推測できる情報、職業・経歴、実在人物の情報、オーナーの作業予定や生活の様子。人は「オーナー」と書き、個人名を書かない
- 秘密情報（APIキー、`.dev.vars` の中身など）
- 実際の服薬情報、実在の人の会話や文字起こし。試験の入力を載せるときは、架空のものだけにする
- 書き終えたら、上の3つが入っていないか読み返す

## 5. 書いた後
- `docs/dev-logs/README.md` の一覧に1行足す（新しいものを下に）。
- その回の `docs/KEEP-THINKING.md` の節に、dev-log のファイル名を1行で書く。
- 引用したファイル名・コミット・PR番号と、それを確かめたコマンドをPR本文に書く。
