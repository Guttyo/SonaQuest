## ADR-0001 開発の仕組み（CLAUDE.mdと.claude/の役割分担）
- 状態：採用　日付：2026-11-02
- 決定：CLAUDE.mdには毎回守る短いルールだけを書く。詳細は `.claude/rules/`（scope・safety・privacy）、手順は `.claude/skills/`、機械的に守らせるものは `.claude/hooks/` とgitのコミット前フック（`.githooks/`）、記録は `docs/` に置く。
- 理由：CLAUDE.mdが長いと毎回の読み込みが重く、ルールが埋もれる。守らせたいことは文書でなくhookで止める方が確実。

- 影響：ルールを変えるときは、該当するrulesとhookの両方を直す。

## ADR-0003 技術構成
- 状態：採用（2026-11-03、オーナーがチャットで採用）　日付：2026-11-02
- 決定：Frontend は React / TypeScript / Vite、Backend は Cloudflare Workers / Hono。DBなし、認証なし。APIキーはWorkersのsecrets（ローカルは `.dev.vars`）で管理し、ブラウザに出さない。
- 理由：静的配信とAPIを1つの無料枠中心の構成で済ませられる。会話を保存しない方針とDBなしが一致する。
- 却下案：Next.js等のフルスタック構成（今回の規模には重い）。ブラウザから直接Claude APIを呼ぶ（キーが露出する）。
- 影響：開発機にNode.jsが必要（2026-11-02にオーナーがNode.js 26 LTSをnvmで導入済み）。
- 外部監査（2026-11-02）の所見：承認してよい構成。条件は、API失敗時に回答と進行を失わないこと、Claudeに送る文字列を最小限にすること、開発時のデバッグログにも会話本文を残さないこと、初期版で外部音声サービスを必須にしないこと。状態を「採用」にするのは、オーナーがMVP着手を承認したとき。
- → オーナー決定（2026-11-03、チャット）：技術方針として採用する。MVPの実装は、別のIssueを立てて進める。
- 公開前の必須条件（2026-11-03、オーナー）：誰でも呼べるClaude APIの呼び出し口（/api/turn）を公開するため、次の3つを公開前に確かめる。満たすまで公開しない（docs/safety-test-plan.md P7〜P9）。
  1. リクエストの回数制限
  2. 入力の大きさの上限（回答の文字数、回答の件数）
  3. Claude APIの支出の上限（Anthropic側の上限設定）

## ADR-0007 ログと保存
- 状態：採用（設定値の確認は実装時）　日付：2026-11-02
- 決定：会話本文・録音・文字起こし・プロンプト・応答を、自アプリのストレージとログに残さない。Workersのコードはこれらを `console.log` に出さない。Workers Logsは無効のままにするか、有効にする場合も `invocation_logs = false` とし、Logpush・Tail Workersは使わない。ブラウザ側も保存しない。
- 理由：防災訓練に会話の保存は不要。服薬に関わる発言は機微な情報になりうる。
- 未確認：Workersの呼び出しログにリクエスト本文が含まれるか（公式文書に記載なし）。実装時に `wrangler tail` で確かめる。
- 影響：不具合調査は本文を含まない値（所要時間、エラー種別、ターン数）で行う。開発時のデバッグログにも本文を出さない。エラー監視サービスは使わない（使う場合は本文が混入しないことを確かめてからADRを追加する）。
- 注意：「保存しない」と「外部に送らない」は別のこと。Claude APIに送った時点で回答は端末の外に出る。README と初回画面ではこの2つを分けて説明する。

## ADR-0008 Claude Codeの自動メモリ
- 状態：採用　日付：2026-11-02
- 決定：自動メモリは使ってよいが補助とし、正本はGit管理の文書（CLAUDE.md、rules、docs）とする。メモリにはプロジェクトの事実を書かず、作業の進め方のフィードバックだけを置く。
- 確認したこと：自動メモリはローカルの `~/.claude/projects/<project>/memory/` に保存され、既定で有効。このセッションでも使えた。無効にするには設定 `autoMemoryEnabled: false` か環境変数 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`。
- 理由：開発過程を審査で示すには、判断がリポジトリに残っている必要がある。メモリはリポジトリの外にあり、公開されず、他の環境に引き継がれない。

## ADR-0009 利用者に薬の名前まで話してもらうか
- 状態：採用（マーカー解除待ち）　日付：2026-11-02
- 決定：
  - → オーナー決定（2026-11-02、チャット）：推奨Aを修正して採用。実際の薬の名前は質問しない。薬の名前を言えるかは評価の対象にせず、情報源を把握しているか、使えないときにどうするかを確かめる。自発的に入力された薬の名前も、原則としてClaudeへ送らない設計にする。
  - → オーナー決定（2026-11-02、第2回監査を受けて変更）：**薬の名前の自動検出・置き換えは初期MVPでは実装しない**。自発的に入力された薬の名前は、そのままClaudeへ送ってよい。「原則として送らない」は取り消す。
  - → オーナー決定（2026-11-03、チャット）：「実際の薬の名前は質問しない」を取り消す。薬の名前・量・病名・何の薬かを質問してよい（ADR-0021）。「薬の名前を言えるかは評価の対象にしない」と下の必須事項は変えない。
- 方式（旧提案。上の変更により採用しない）：
  1. 開始前の案内で「氏名や薬の名前など実際の情報は入れず、在りかや手段だけで答える。架空の内容で答えてもよい」と伝える。
  2. 送信前に、薬の名前らしい語（「〜錠」「〜カプセル」「〜mg」など）をブラウザ側で「［薬の名前］」に置き換える。完全には取り除けないことを初回画面と README に書く。
  3. 結果画面の原文表示は端末内だけで行う（置き換え前の文は送らない）。
  - → オーナー決定（2026-11-02、第2回監査）：1〜3の方式は採用しない。代わりに下の「必須事項」を採用する。
- 必須事項（2026-11-02 決定）：
  1. 利用開始時に、入力内容がAnthropic（Claude API）へ送られることを明示する。
  2. 氏名・住所・電話番号・実際の患者情報を入力しないよう案内する。
  3. 架空の薬の情報でも訓練できることを明記する。
  4. Claudeに、薬の名前の修正、薬効の評価、服薬の適否の判断をさせない。
  5. 結果画面の原文は、端末内に保持した利用者の入力から表示する。Claudeの生成結果を原文として扱わない（原文をClaudeの応答から復元しない）。
  6. 会話本文をアプリ側で永続保存・ログ出力しない（ADR-0007）。
  7. 薬の名前の有無によって、個別の医療判断を行わない。
  - Claudeへ送るデータは、訓練に必要な範囲（これまでの回答とターン番号）に限る。
- 利用開始画面の文面（第2回監査の案）：
  > このアプリは災害時の服薬情報の伝え方を練習するものです。入力した内容は会話を進めるためにAIサービス（Anthropic）へ送信されます。氏名、住所、電話番号などは入力せず、架空の情報でも練習できます。薬の正確性や治療の適否は判定しません。
- 実際の服薬情報を入力できるサービスにするか、架空の情報だけで練習するサービスにするか：[TODO-OWNER: 実際の服薬情報の入力を許すか（監査の推奨：入力はできるが架空の情報を推奨）]
  - → オーナー決定（2026-11-03、チャット）：**架空の情報だけで練習するサービスにする**。利用者には、本人やほかの人の実際の服薬情報を入力しないよう案内し、架空の内容で答えてもらう。必須事項3の「架空の薬の情報でも訓練できる」は「架空の薬の情報で訓練する」と読み替える。入力された内容が実際の情報かどうかをアプリは確かめられないので、入力されても保存・ログ出力しない扱い（必須事項6）は変えない。
  - 今後の課題（2026-11-03、オーナー）：サービスとして公開（ローンチ）するときは、利用者が自分の実際の服薬状況を示せることが必要になる。ハッカソンの提出版は架空のみとし、実際の情報を扱う版は、別のADRで条件を決めてから作る。決めるときに確かめる項目の候補（Claude Codeの整理。結論ではない）：
    - 服薬情報・病名は個人情報保護法の要配慮個人情報にあたりうるため、取得と外部送信への本人の同意の取り方
    - 外部事業者（Anthropic など）の保持期間と、ゼロ保持などの契約の要否（ADR-0006）
    - 保存しない方針（ADR-0007）を続けるか、続けないなら保存の範囲・期間・削除の方法
    - 薬の名前を含む入力に対しても、医療判断をしないことの再点検（safety-test-plan S1〜S10）と、医療機器の規制にあたらないことの確認
    - 実際の服薬状況を結果画面でどう示すか（原文のまま表示する方針、ADR-0009 必須事項5）
- 理由：訓練の目的は情報の伝え方であり、薬の名前の正確さは評価しない。不完全な自動フィルタは、訓練の記録（利用者が何を伝えたか）を損ない、商品名・略称・音声認識の誤変換に対応できず、実装と検証の負担を増やす。大事なのは、入力内容を医療判断に使わないことと、外部へ送ることを利用者が理解していること。
- 却下案：正規表現による薬の名前の置き換え（上の理由）。

## ADR-0013 リポジトリの公開時期とコミットの名義
- 状態：採用　日付：2026-11-02
- 決定：開発中はGitHubのプライベートリポジトリに置き、提出時に公開する。コミットの名義は名前 `Guttyo`、メールはGitHubのnoreplyアドレスとし、個人のメールアドレスを履歴に残さない。プライベートリポジトリの作成・push・公開の切り替えは、それぞれオーナーの承認を得てから行う。
- 理由：公式ルールで提出時点の公開が必要。開発途中を公開する必要はない。
- 影響：公開すると過去のコミットもすべて見えるようになる。そのため、プライベートの間も公開してよい内容だけをコミットする（コミット前フックとブロックリストで確認する）。

## ADR-0014 GitHub運用とhookの位置づけ
- 状態：採用（GitHub側の設定は未実施）　日付：2026-11-02
- 決定：すべての変更を Issue → `main` からの専用ブランチ → PR → オーナーの明示的な承認後のマージ で行う。`main` への直接コミット・直接push・force push・削除をしない。詳細は `.claude/rules/github.md`。
- GitHub側の保護設定（案）：PR必須、force push禁止、削除禁止、CI成功必須。第三者のレビュー承認1件は必須にしない。設定の変更はオーナーの承認を得てから行う。
- ローカルの補助：コミット前フックが `main` へのコミットを止める。Claude Codeのhookが、force push、`main` へのpush、PRのマージ、`main` の削除、保護設定の変更を止める。
- 正とするもの：`main` の保護は**GitHubのRulesetを正**とする。ローカルのhookは、Claude Codeを通した誤操作を防ぐ補助で、Claude Codeを通さない操作は守れない。gitの pre-merge-commit は fast-forward マージでは呼ばれないので、オーナーが手で `main` 上の fast-forward マージをしても止まらない（Claude Codeのhookは `main` 上の `git merge` を止める）。Rulesetを設定するまでは運用で守る（`.claude/rules/github.md`）。
- hookの位置づけ：hookは誤操作を防ぐ補助であり、セキュリティの境界ではない。`SONAQUEST_OWNER_APPROVED=1` は本人確認ではない。オーナーの承認はチャットでの明示とPRの記録で成立する。秘密情報は、公開前にGit履歴全体の検査と、Cloudflareのsecretsの確認を別途行う。
- 理由：単独開発でも変更の単位と判断の記録をPRに残すため。自分のPRは自分で承認できないので、レビュー必須にするとマージできなくなる。
- 却下案：`main` へ直接コミットする運用（判断の記録が残らない）。レビュー承認1件を必須にする（単独では詰まる）。
- 影響：この変更（Phase 0の運用追加）は、GitHubリポジトリがまだ無いため、Issue番号のないローカルブランチ `docs/phase0-github-rules` で作業した。リポジトリ作成の承認後にIssueを作って関連付ける。初回コミット 1e993f3 は、この運用を決める前に `main` へ直接入れたもの。

## ADR-0017 5観点の判定は3段階
- 状態：採用（マーカー解除待ち。基準は docs/PRD.md）　日付：2026-11-02
- 決定：観点ごとに「確認できた」「未確認と気づいた」「確認していない」の3段階で示す。API失敗時は「判定できませんでした」を加える。「知らない」「確認できない」と答えたことも、大事な気づきとして扱う。
- 理由：知識の正誤をAIに判定させずに、訓練で見つかった課題を示せる。二値だと「わからないと気づけた」ことが「できなかった」に埋もれる。
- 影響：正解ラベル（docs/evidence.md）は3段階で付ける。基準と正解ラベルは人間（オーナー）が決める。
- 意味の限定（2026-11-02、第2回監査）：「確認できた」は、その観点について**利用者が説明できた（発言内容を確認できた）**という意味であり、内容の正確さや、実際にその薬を飲んでいるという事実を保証するものではない。結果画面にもこの区別を書く。

## ADR-0018 Dropbox上のGitリポジトリの扱い
- 状態：採用　日付：2026-11-02
- 背景：リポジトリはDropboxの同期フォルダにあり、`.git` もWindowsとmacOSの間で同期される。両方の端末でGit操作をすると、同期の競合や `.git` 内の不整合が起きうる。
- 決定：
  - WindowsとmacOSで同時にGit操作をしない。
  - 端末を切り替える前に、Dropboxの同期が終わったことを確かめる。
  - GitHubにリモートリポジトリを作った後は、GitHubを正本とする。各端末ではGitHubからcloneした作業コピーを使い、変更はGitHub経由で同期する方式へ移る（移る時期と置き場所はオーナーが決める）。
- 理由：ハッカソン期間中にフォルダを移す手間は避けたいが、同期の競合で履歴が壊れる危険は避けたい。
- 却下案：Dropbox同期のまま両端末で自由にGit操作する。

## ADR-0019 体験の核を「お薬の避難訓練」として定める
- 状態：提案中（採用案。オーナーの指示 2026-11-03 を反映）　日付：2026-11-03（Issue #6）
- 背景：再監査（2026-11-03、Issue #6）で、PRDに機能要件はあるが、企画段階のコンセプト「お薬の避難訓練」と、情報源を失った後に伝え直す体験が仕様として残っていないと指摘された。このまま実装すると、一般的な問診チャットや防災チェックリストに近くなるおそれがある。企画段階（2026-11-02の再検討）の6段階は、はじめに／問い／確認／出来事／立て直し／結果だった。その後、実装の画面を「はじめに／対話／振り返り」の3つにまとめる案も検討した。
- 決定（採用案）：
  - コンセプトを「お薬の避難訓練」、訴求文を「もしもの時、自分の薬のことを伝えられますか？」とし、PRDの冒頭に置く。訓練の中心は、情報源を1つ失った後、残った手段で伝え直す体験とする。
  - 体験は企画段階の6段階（① はじめに → ② 問い → ③ 確認 → ④ 出来事 → ⑤ 立て直し → ⑥ 結果）とする。6つの独立した画面は必須にせず、実装は「はじめに／対話／振り返り」の3画面を基本とする。
  - ③確認では、②の回答から一番頼りにしている情報源を出来事の6候補の分類で初期選択にし、本人がタップで確かめるか直す。出来事は本人が確かめた分類からルールで選ぶ（ADR-0016）。タップは回答の回数に数えない。
  - 回答は最大6回（②問いで最大3回、⑤立て直しで最大3回が目安）。聞き返しも回数に含める。何を優先して聞くかは5観点の未確認のことに基づき、6回すべてに答えさせる必要はない。
  - ⑤の最初の質問は、固定の立て直しの問い（「では、ほかにどうやって伝えられますか？」）にし、必ず1回出す。Claudeには作らせない。
  - 観点②（代わりの手段）は、主に出来事の後の回答で確かめる。使えなくなった情報源に依存しない、具体的な別の手段を挙げた → 確認できた。代わりの手段を知らないと本人が言葉にした → 未確認と気づいた。手段を挙げられたかだけを見て、医学的な正誤は判定しない。
  - 点数・順位・合否で評価しない。結果には観点ごとの3段階と回答の原文（出来事の前後に分ける）を出し、「確認していない」「未確認と気づいた」の観点を「手薄なところ」として示す。準備行動を1つ選び、固定文には出典と確認日を添える。
- 理由：情報源を失うだけなら防災クイズになる。その後に残った手段で伝え直すことが、この作品を「避難訓練」にする。本人が実際には頼っていない情報源を失わせると立て直しの体験にならないので、出来事の前に本人の確認を挟む。確認をタップにすれば、6回の回答の枠を訓練の本体に使える。画面を3つにまとめるのは、ハッカソンの時間で作り切るため。新しい機能は増やさず、既に決めた要素（出来事の6候補、5観点、3段階、準備行動）を、どの順序でどう体験させるかを決めるもの。
- 却下案：
  - 出来事を対話の任意の時点で起こす（立て直しの回答が残らないことがある）。
  - 本人の確認を省き、回答から推定した情報源で出来事を起こす（頼っていない情報源を失わせるおそれがある）。
  - 確認を自由記述の回答として数える（6回の枠が減る）。
  - 6段階をそれぞれ独立した画面にする（作る量が増える。体験の段階は対話の画面の中で表せる）。
  - 立て直しの問いをClaudeに作らせる（固定文から選ぶ方針と、固定質問方式との比較の条件に反する）。
  - 点数を出して達成感を出す（未確認を「できなかった」と受け取らせ、気づきの目的に反する）。
- 影響：PRD（コンセプト、体験の核、6段階と実装の画面、③確認、回答の配分、立て直しの判定、評価の方針）、architecture（Claudeを使わずに決める部分、/api/turn の入力）、demo-script、evidence（立て直しの測定）。固定の6問（ADR-0012）と比較実験の方式A（docs/evidence.md）も、前半3問 → 確認 → 出来事 → 後半3問の並びにする。③の初期選択の決め方（語の照合、Claudeの構造化出力）は実装時に別のADRで決める。

## ADR-0020 聞き取り係を光のキャラクターとして表す

## ADR-0021 薬の名前・量・病名・種類を聞いてよい
- 状態：採用（2026-11-03、オーナーがチャットで決定）　日付：2026-11-03（Issue #8）
- 背景：試作版の通しで、オーナーが「聞き取りが微妙」と感じた。最初の質問に「血圧の薬を飲んでいますね」と答え、「他にどんな薬を飲んでいるか聞かないの？」と感じた。公式の手引き（README「参考にした公式資料」）を調べると、実際の聞き取りは、普段の薬があるか → 何で確かめられるか → ほかの病院の薬・市販薬 → アレルギー・副作用 → いつから・最近の変化 → 今飲めているか → 誰が管理しているか、の順で、薬の中身も聞いている。ADR-0009 で「実際の薬の名前は質問しない」としていたため、質問が不自然になっていた。
- 決定：薬の名前・量・病名・何の薬か（種類）を、実際の聞き取りに合わせて質問してよい。オーナーの条件は次のとおり。
  - アプリは答えを原文のまま返す（表示する）だけ
  - Claudeは診断も判断もしない（薬の名前の修正、薬効の評価、正誤の判定、服薬の適否の判断をしない）
  - 記録しない（ADR-0007）
- 変えないこと：薬の名前を言えたかどうかは評価しない。5観点と3段階の判定（ADR-0017）、ADR-0009 の必須事項（送信の明示、架空の情報でも練習できる、原文は端末内の入力から表示、薬の名前の有無で個別の医療判断をしない）。
- 理由：中身を聞かない質問は、実際の救護所の聞き取りと違い、訓練の場面として不自然になる。薬の名前や量を答えられるかどうか自体も、利用者の気づきの材料になる（日本薬剤師会の事例集に、薬効の言い方でしか伝えられず処方が合わなかった例がある）。アプリが答えを判定しないので、聞くこと自体は医療判断にあたらない。
- 却下案：中身は聞かず、在りかと手段だけを聞く（ADR-0009 の当初の方針。質問が不自然で、実際の聞き取りの練習にならない）。
- 影響：
  - `.claude/rules/safety.md`、PRD、README の「薬の名前は尋ねません」の記載を直す。固定の質問文と利用開始の案内（`web/src/flow/content.ts`）を直す。
  - 実際の服薬情報が入力されやすくなる。ADR-0009 の必須事項2（実際の患者情報を入力しないよう案内する）と、オーナーの判断待ちの「実際の服薬情報の入力を許すか」（ADR-0009）との関係は、オーナーの判断が要る。それまでは「架空の内容でも練習できる」を案内に残す。
  - Claude連携の後は、薬の名前を含む回答が Anthropic へ送られる。初回画面の説明（送信の明示）はそのまま必要。
  - 固定の質問の順番は、手引きの順番をもとに、後半を「代わりの手段 → 最近の変化・飲めているか → 薬を知っている人」とした（6問の枠に収めるための調整）。
