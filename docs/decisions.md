## ADR-0001 開発の仕組み（CLAUDE.mdと.claude/の役割分担）
- 状態：採用　日付：2026-11-02
- 決定：CLAUDE.mdには毎回守る短いルールだけを書く。詳細は `.claude/rules/`（scope・safety・privacy）、手順は `.claude/skills/`、機械的に守らせるものは `.claude/hooks/` とgitのコミット前フック（`.githooks/`）、記録は `docs/` に置く。

## ADR-0003 技術構成
- 状態：採用（2026-11-03、オーナーがチャットで採用）　日付：2026-11-02
- 決定：Frontend は React / TypeScript / Vite、Backend は Cloudflare Workers / Hono。DBなし、認証なし。APIキーはWorkersのsecrets（ローカルは `.dev.vars`）で管理し、ブラウザに出さない。
- 理由：静的配信とAPIを1つの無料枠中心の構成で済ませられる。会話を保存しない方針とDBなしが一致する。
- 却下案：Next.js等のフルスタック構成（今回の規模には重い）。ブラウザから直接Claude APIを呼ぶ（キーが露出する）。
- 影響：開発機にNode.jsが必要（2026-11-02にオーナーがNode.js 26 LTSをnvmで導入済み）。
- 外部監査（2026-11-02）の所見：承認してよい構成。条件は、API失敗時に回答と進行を失わないこと、Claudeに送る文字列を最小限にすること、開発時のデバッグログにも会話本文を残さないこと、初期版で外部音声サービスを必須にしないこと。状態を「採用」にするのは、オーナーがMVP着手を承認したとき。
- → オーナー決定（2026-11-03、チャット）：技術方針として採用する。MVPの実装は、別のIssueを立てて進める。
- 公開前の必須条件（2026-11-03、オーナー）：誰でも呼べるClaude APIの呼び出し口（/api/turn）を公開するため、次の3つを公開前に確かめる。満たすまで公開しない（docs/safety-test-plan.md P7〜P9）。
  1. リクエストの回数制限
  2. 入力の大きさの上限（回答の文字数、回答の件数）
  3. Claude APIの支出の上限（Anthropic側の上限設定）

## ADR-0004 音声認識

| 遅延 | 公称の中央値 約150ms（ネットワーク除く） | 未測定 |

## ADR-0005 音声合成
- 状態：採用（2026-11-03、オーナーがチャットで決定。Issue #19。音声ファイルの公開は下のマーカー）　日付：2026-11-02（下の表は 2026-11-02 の調査）

| 観点 | ElevenLabs Flash v2.5（または後継） | ブラウザ標準 speechSynthesis |
|---|---|---|
| 料金 | 約$0.04/1,000文字 | 無料 |
| 遅延 | 公称 約75〜100ms（ネットワーク除く） | 端末内。未測定 |
| 日本語 | 対応 | iOS 16以降、日本語音声がgetVoices()に出ない不具合報告あり（現状は未確認） |
| 保持方針 | ADR-0004と同じ（ゼロ保持はEnterpriseのみ） | 端末内で完結（と想定。未確認） |
| iPhone Safari | 音声ファイルの再生。自動再生の制限に注意 | ユーザー操作の後でないと話さない制限。消音スイッチの影響 |

- 外部監査（2026-11-02）の推奨：初期版では外部音声サービス（ElevenLabs）を採用せず、まず文字入力で体験が成り立つかを確かめる。ADR-0004も同じ扱いにする案。オーナーの判断待ち。→ 2026-11-03 のオーナーの決定（下）で整理した。
- 方針（案、2026-11-02）：まずブラウザ標準で一連の体験を作り、質の差がデモの評価に響くと判断したらElevenLabsを試す。質問文は固定文が多いので、事前に合成した音声ファイルを同梱する案も比べる（外部送信なし）。
- 動作の要件：ウェブブラウザで動けばよく、iPhone 実機で見せなくてよい（オーナー決定 2026-11-03、Issue #17）。上の表の iPhone Safari の行は調査の記録として残し、要件にはしない。自動再生の制限（利用者の操作の後でないと再生しない）はほかのブラウザにもあるので、最初のタップまで再生を待つ設計は残す。
- → オーナー決定（2026-11-03、チャット）：音声合成は ElevenLabs にする。キーはオーナーが用意済みで、リポジトリには入れない。
- 決定の中身（Claude Code の整理）：
  - ElevenLabs は Workers の中継で呼び、キーは Workers の secrets にだけ置く（ブラウザに出さない）。ElevenLabs に送るのは読み上げる文（Claude の質問文や固定文）だけで、利用者の回答は送らない。
  - ElevenLabs が失敗・時間切れのときは、ブラウザの読み上げ（speechSynthesis）に切り替える。外部監査の「初期版で外部音声サービスを必須にしない」は、この切り替えがあるので保たれる。文字の表示だけでも訓練は最後まで進む（ADR-0012）。
  - 音声の会話が間に合わないときの代わり（案、2026-11-03）：決まった文面（固定の質問文など）を事前に音声ファイルにして同梱し、決まった文面の音声のやり取りだけでデモにする（上の「方針（案）」の同梱の案）。→ 下のオーナー決定で、同梱しないことにした。
  - オーナーが判断した点：オーナーのクローン音声で作った音声ファイルを公開リポジトリに入れてよいか
  - → オーナー決定（2026-11-03、チャット）：リポジトリに固定の音声ファイルは入れない（不要）。オーナーの声は、ElevenLabs の API 経由で使えるようにできる見込み（オーナーの言葉は「ElevenLabsのAPI経由で僕の声使えるようにできると思うよ。リポジトリには固定の音声ファイルは不要です。」）。
  - 上の決定による影響（Claude Code の整理）：オーナーの声を使う場合も、声の指定（ElevenLabs の voice ID）はリポジトリに書かず、Workers の設定（secrets）に置く案。読み上げが失敗したときは、ブラウザの読み上げに切り替える（上のとおり）。
- 参考にした設計（考え方だけ。コードは複製しない。CLAUDE.md 絶対ルール1）：オーナーが示した Guttyo/virtual-puppet-theater（他の作者の作品のフォーク、MIT）の音声のやり取り。
  - 音声認識は1回の発話ごとに認識し、終わったら自動で再開する。途中経過の文がしばらく変わらなければ、確定を待たずに回答として扱う（ADR-0010 の確認と修正は残す）。
  - 読み上げは順番待ちにし、利用者が話し始めたら止める。ブラウザの自動再生の制限に合わせ、最初のタップまで再生を待つ。
  - 失敗した外部サービスは、その回の残りでは呼ばずにブラウザの読み上げに切り替える。
  - 参考元は、認識した文と読み上げる文をコンソールに出している。SonaQuest では、公開する版では出さない（ADR-0007「開発中だけのログ出力」）。
- 影響（直す箇所。直すのは音声を実装する Issue で行う）：
  - README「外部事業者に送るもの」：音声認識（ブラウザが使うサービス。ブラウザによって違い、Google・Apple と見られるが未確認）と ElevenLabs を足す。ElevenLabs には読み上げる文だけを送り、回答は送らないと書く
  - 初回画面の送信の説明（`web/src/flow/content.ts` の `INTRO_LEAD`・`PRIVACY_EXTERNAL`）と、ADR-0009 の利用開始の文面：送信先に音声認識と ElevenLabs を足す
  - 保持方針：Google（音声認識）と ElevenLabs の公表している保持方針を、確かめた日付つきで書く。確かめられないものは「未確認」と書く（2026-11-03 時点ではどちらも未確認。ElevenLabs は 2026-11-02 の調査で「既定で履歴を保持、ゼロ保持は Enterprise のみ」）
  - docs/architecture.md の構成図（ELEVENLABS_API_KEY を「採用時のみ」から必須でない secrets に）、docs/safety-test-plan.md の P4（送信先の一致）と F4・F5

## ADR-0007 ログと保存
- 状態：採用（設定値の確認は実装時）　日付：2026-11-02
- 決定：会話本文・録音・文字起こし・プロンプト・応答を、自アプリのストレージとログに残さない。Workersのコードはこれらを `console.log` に出さない。Workers Logsは無効のままにするか、有効にする場合も `invocation_logs = false` とし、Logpush・Tail Workersは使わない。ブラウザ側も保存しない。
- 理由：防災訓練に会話の保存は不要。服薬に関わる発言は機微な情報になりうる。
- 未確認：Workersの呼び出しログにリクエスト本文が含まれるか（公式文書に記載なし）。実装時に `wrangler tail` で確かめる。
- 影響：不具合調査は本文を含まない値（所要時間、エラー種別、ターン数）で行う。開発時のデバッグログにも本文を出さない。エラー監視サービスは使わない（使う場合は本文が混入しないことを確かめてからADRを追加する）。
- 注意：「保存しない」と「外部に送らない」は別のこと。Claude APIに送った時点で回答は端末の外に出る。README と初回画面ではこの2つを分けて説明する。
- 追記：開発中だけのログ出力（状態：採用。2026-11-03、オーナーがチャットで決定。Issue #19）
  - 変更：保存しないことは変えない。**公開する版（デプロイした Workers。本番・プレビューとも）と本番用にビルドしたブラウザのコード**では、会話本文・音声・プロンプト・Claude の応答をログに出さない。手元の開発中（`wrangler dev`、`npm run dev`）に限り、確認のために本文を出してよい。上の「開発時のデバッグログにも本文を出さない」をこのとおり緩める。
  - 理由：Claude と音声をつなぐと、プロンプトと応答を見ないと不具合を直せない。手元の開発機の画面に出すだけなら、保存にも外部送信にもあたらない。公開する版で出さなければ、Workers のログや Cloudflare 側に本文が残らない。
  - 仕組み（案）：切り替えは既定でオフにし、二重に守る。
    1. Workers：環境変数 `DEV_CONTENT_LOG` が `"1"` で、**かつ**リクエストの宛先が `localhost`・`127.0.0.1` のときだけ本文を出す。`DEV_CONTENT_LOG` は `wrangler.toml` に書かず、手元で `wrangler dev --var DEV_CONTENT_LOG:1` と指定したときだけ有効にする。設定が誤ってデプロイに入っても、宛先の条件で出ない。
    2. ブラウザ：Vite の `import.meta.env.DEV` が真で、**かつ** `import.meta.env.MODE === "development"` のとき（開発用サーバー）だけ出す。`DEV` だけだと、シェルや `.env` の `NODE_ENV` によっては `vite build` でも真になるため（Issue #19 のレビュー）。`vite build` の MODE は既定で `production` なので、この分岐は本番用のビルドから取り除かれる。
    3. 本文を出す処理は1つの関数にまとめ、上の条件を単体試験で確かめる。デプロイ後に safety-test-plan P1（`wrangler tail` で本文が出ない）を、公開の前に P11（ビルド成果物に本文を出す処理が残っていない）を確かめる。
    4. Workers の宛先の条件は、利用者が書き換えられる `Host` ヘッダーではなく、`request.url` の hostname で見る。デプロイした Workers の `request.url` は公開のドメインになり、`localhost` にはならない見込み（実装時に確かめる）。それでも `DEV_CONTENT_LOG` を `wrangler.toml` に書かないことと、デプロイ前の確認（P1）を主な守りとする。
  - 守ること：開発中に出した本文を、ファイル・Issue・PR・コミット・dev-log に貼らない（`.claude/rules/privacy.md`）。試験には架空の入力だけを使う。
  - 却下案：開発中も一切出さない（不具合の調査が難しい）。環境変数だけで切り替える（デプロイの設定の誤りで本番に出るおそれ）。
  - オーナーが判断した点：ログ出力の緩和（開発中のみ可）と、その仕組み
  - → オーナー決定（2026-11-03、チャット）：採用する。公開する版では本文をログに出さず、手元の開発中だけ（`DEV_CONTENT_LOG` と宛先が localhost の両方のとき）本文を出してよい。

## ADR-0008 Claude Codeの自動メモリ
- 状態：採用　日付：2026-11-02
- 決定：自動メモリは使ってよいが補助とし、正本はGit管理の文書（CLAUDE.md、rules、docs）とする。メモリにはプロジェクトの事実を書かず、作業の進め方のフィードバックだけを置く。
- 確認したこと：自動メモリはローカルの `~/.claude/projects/<project>/memory/` に保存され、既定で有効。このセッションでも使えた。無効にするには設定 `autoMemoryEnabled: false` か環境変数 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`。
- 理由：開発過程を審査で示すには、判断がリポジトリに残っている必要がある。メモリはリポジトリの外にあり、公開されず、他の環境に引き継がれない。

## ADR-0009 利用者に薬の名前まで話してもらうか
- 状態：採用　日付：2026-11-02
- 決定：
  - → オーナー決定（2026-11-02、チャット）：推奨Aを修正して採用。実際の薬の名前は質問しない。薬の名前を言えるかは評価の対象にせず、情報源を把握しているか、使えないときにどうするかを確かめる。自発的に入力された薬の名前も、原則としてClaudeへ送らない設計にする。
  - → オーナー決定（2026-11-02、第2回監査を受けて変更）：**薬の名前の自動検出・置き換えは初期MVPでは実装しない**。自発的に入力された薬の名前は、そのままClaudeへ送ってよい。「原則として送らない」は取り消す。
  - → オーナー決定（2026-11-03、チャット）：「実際の薬の名前は質問しない」を取り消す。薬の名前・量・病名・何の薬かを質問してよい（ADR-0021）。「薬の名前を言えるかは評価の対象にしない」と下の必須事項は変えない。
- 方式（旧提案。上の変更により採用しない）：
  1. 開始前の案内で「氏名や薬の名前など実際の情報は入れず、在りかや手段だけで答える。架空の内容で答えてもよい」と伝える。
  2. 送信前に、薬の名前らしい語（「〜錠」「〜カプセル」「〜mg」など）をブラウザ側で「［薬の名前］」に置き換える。完全には取り除けないことを初回画面と README に書く。
  3. 結果画面の原文表示は端末内だけで行う（置き換え前の文は送らない）。
  - → オーナー決定（2026-11-02、第2回監査）：1〜3の方式は採用しない。代わりに下の「必須事項」を採用する。
- 必須事項（2026-11-02 決定）：
  1. 利用開始時に、入力内容がAnthropic（Claude API）へ送られることを明示する。
  2. 氏名・住所・電話番号・実際の患者情報を入力しないよう案内する。
  3. 架空の薬の情報でも訓練できることを明記する。
  4. Claudeに、薬の名前の修正、薬効の評価、服薬の適否の判断をさせない。
  5. 結果画面の原文は、端末内に保持した利用者の入力から表示する。Claudeの生成結果を原文として扱わない（原文をClaudeの応答から復元しない）。
  6. 会話本文をアプリ側で永続保存・ログ出力しない（ADR-0007）。
  7. 薬の名前の有無によって、個別の医療判断を行わない。
  - Claudeへ送るデータは、訓練に必要な範囲（これまでの回答とターン番号）に限る。
- 利用開始画面の文面（第2回監査の案）：
  > このアプリは災害時の服薬情報の伝え方を練習するものです。入力した内容は会話を進めるためにAIサービス（Anthropic）へ送信されます。氏名、住所、電話番号などは入力せず、架空の情報でも練習できます。薬の正確性や治療の適否は判定しません。
- 実際の服薬情報を入力できるサービスにするか、架空の情報だけで練習するサービスにするか（オーナーが判断した点。監査の推奨：入力はできるが架空の情報を推奨）：
  - → オーナー決定（2026-11-03、チャット）：**架空の情報だけで練習するサービスにする**。利用者には、本人やほかの人の実際の服薬情報を入力しないよう案内し、架空の内容で答えてもらう。必須事項3の「架空の薬の情報でも訓練できる」は「架空の薬の情報で訓練する」と読み替える。入力された内容が実際の情報かどうかをアプリは確かめられないので、入力されても保存・ログ出力しない扱い（必須事項6）は変えない。
  - 今後の課題（2026-11-03、オーナー）：サービスとして公開（ローンチ）するときは、利用者が自分の実際の服薬状況を示せることが必要になる。ハッカソンの提出版は架空のみとし、実際の情報を扱う版は、別のADRで条件を決めてから作る。決めるときに確かめる項目の候補（Claude Codeの整理。結論ではない）は `docs/roadmap.md` の「1. 実際の服薬状況を扱う版」に移した（Issue #16）。
  - → オーナー決定（2026-11-03、チャット、Issue #12）：「架空のみ」は**薬の中身**（名前・量・病名・ほかの薬・アレルギー・飲めているか）に限る。情報の在りか、ほかの伝え方、薬を知っている人（続柄など）、記録が新しいかは、本人のこととして振り返って答える（ADR-0022 の案B）。
- 理由：訓練の目的は情報の伝え方であり、薬の名前の正確さは評価しない。不完全な自動フィルタは、訓練の記録（利用者が何を伝えたか）を損ない、商品名・略称・音声認識の誤変換に対応できず、実装と検証の負担を増やす。大事なのは、入力内容を医療判断に使わないことと、外部へ送ることを利用者が理解していること。
- 却下案：正規表現による薬の名前の置き換え（上の理由）。

## ADR-0014 GitHub運用とhookの位置づけ
- 状態：採用（GitHub側の設定は未実施）　日付：2026-11-02
- 決定：すべての変更を Issue → `main` からの専用ブランチ → PR → オーナーの明示的な承認後のマージ で行う。`main` への直接コミット・直接push・force push・削除をしない。詳細は `.claude/rules/github.md`。
- GitHub側の保護設定（案）：PR必須、force push禁止、削除禁止、CI成功必須。第三者のレビュー承認1件は必須にしない。設定の変更はオーナーの承認を得てから行う。
- ローカルの補助：コミット前フックが `main` へのコミットを止める。Claude Codeのhookが、force push、`main` へのpush、PRのマージ、`main` の削除、保護設定の変更を止める。
- 正とするもの：`main` の保護は**GitHubのRulesetを正**とする。ローカルのhookは、Claude Codeを通した誤操作を防ぐ補助で、Claude Codeを通さない操作は守れない。gitの pre-merge-commit は fast-forward マージでは呼ばれないので、オーナーが手で `main` 上の fast-forward マージをしても止まらない（Claude Codeのhookは `main` 上の `git merge` を止める）。Rulesetを設定するまでは運用で守る（`.claude/rules/github.md`）。
- hookの位置づけ：hookは誤操作を防ぐ補助であり、セキュリティの境界ではない。`SONAQUEST_OWNER_APPROVED=1` は本人確認ではない。オーナーの承認はチャットでの明示とPRの記録で成立する。秘密情報は、公開前にGit履歴全体の検査と、Cloudflareのsecretsの確認を別途行う。
- 理由：単独開発でも変更の単位と判断の記録をPRに残すため。自分のPRは自分で承認できないので、レビュー必須にするとマージできなくなる。
- 却下案：`main` へ直接コミットする運用（判断の記録が残らない）。レビュー承認1件を必須にする（単独では詰まる）。
- 影響：この変更（Phase 0の運用追加）は、GitHubリポジトリがまだ無いため、Issue番号のないローカルブランチ `docs/phase0-github-rules` で作業した。リポジトリ作成の承認後にIssueを作って関連付ける。初回コミット 1e993f3 は、この運用を決める前に `main` へ直接入れたもの。

## ADR-0017 5観点の判定は3段階
- 状態：採用（マーカー解除待ち。基準は docs/PRD.md）　日付：2026-11-02
- 決定：観点ごとに「確認できた」「未確認と気づいた」「確認していない」の3段階で示す。API失敗時は「判定できませんでした」を加える。「知らない」「確認できない」と答えたことも、大事な気づきとして扱う。
- 理由：知識の正誤をAIに判定させずに、訓練で見つかった課題を示せる。二値だと「わからないと気づけた」ことが「できなかった」に埋もれる。
- 影響：正解ラベル（docs/evidence.md）は3段階で付ける。基準と正解ラベルは人間（オーナー）が決める。
- 意味の限定（2026-11-02、第2回監査）：「確認できた」は、その観点について**利用者が説明できた（発言内容を確認できた）**という意味であり、内容の正確さや、実際にその薬を飲んでいるという事実を保証するものではない。結果画面にもこの区別を書く。

## ADR-0018 Dropbox上のGitリポジトリの扱い
- 状態：採用　日付：2026-11-02
- 背景：リポジトリはDropboxの同期フォルダにあり、`.git` もWindowsとmacOSの間で同期される。両方の端末でGit操作をすると、同期の競合や `.git` 内の不整合が起きうる。
- 決定：
  - WindowsとmacOSで同時にGit操作をしない。
  - 端末を切り替える前に、Dropboxの同期が終わったことを確かめる。
  - GitHubにリモートリポジトリを作った後は、GitHubを正本とする。各端末ではGitHubからcloneした作業コピーを使い、変更はGitHub経由で同期する方式へ移る（移る時期と置き場所はオーナーが決める）。
- 理由：ハッカソン期間中にフォルダを移す手間は避けたいが、同期の競合で履歴が壊れる危険は避けたい。
- 却下案：Dropbox同期のまま両端末で自由にGit操作する。

## ADR-0019 体験の核を「お薬の避難訓練」として定める
- 状態：提案中（採用案。オーナーの指示 2026-11-03 を反映）　日付：2026-11-03（Issue #6）
- 背景：再監査（2026-11-03、Issue #6）で、PRDに機能要件はあるが、企画段階のコンセプト「お薬の避難訓練」と、情報源を失った後に伝え直す体験が仕様として残っていないと指摘された。このまま実装すると、一般的な問診チャットや防災チェックリストに近くなるおそれがある。企画段階（2026-11-02の再検討）の6段階は、はじめに／問い／確認／出来事／立て直し／結果だった。その後、実装の画面を「はじめに／対話／振り返り」の3つにまとめる案も検討した。
- 決定（採用案）：
  - コンセプトを「お薬の避難訓練」、訴求文を「もしもの時、自分の薬のことを伝えられますか？」とし、PRDの冒頭に置く。訓練の中心は、情報源を1つ失った後、残った手段で伝え直す体験とする。
  - 体験は企画段階の6段階（① はじめに → ② 問い → ③ 確認 → ④ 出来事 → ⑤ 立て直し → ⑥ 結果）とする。6つの独立した画面は必須にせず、実装は「はじめに／対話／振り返り」の3画面を基本とする。
  - ③確認では、②の回答から一番頼りにしている情報源を出来事の6候補の分類で初期選択にし、本人がタップで確かめるか直す。出来事は本人が確かめた分類からルールで選ぶ（ADR-0016）。タップは回答の回数に数えない。
  - 回答は最大6回（②問いで最大3回、⑤立て直しで最大3回が目安）。聞き返しも回数に含める。何を優先して聞くかは5観点の未確認のことに基づき、6回すべてに答えさせる必要はない。
  - ⑤の最初の質問は、固定の立て直しの問い（「では、ほかにどうやって伝えられますか？」）にし、必ず1回出す。Claudeには作らせない。
  - 観点②（代わりの手段）は、主に出来事の後の回答で確かめる。使えなくなった情報源に依存しない、具体的な別の手段を挙げた → 確認できた。代わりの手段を知らないと本人が言葉にした → 未確認と気づいた。手段を挙げられたかだけを見て、医学的な正誤は判定しない。
  - 点数・順位・合否で評価しない。結果には観点ごとの3段階と回答の原文（出来事の前後に分ける）を出し、「確認していない」「未確認と気づいた」の観点を「手薄なところ」として示す。準備行動を1つ選び、固定文には出典と確認日を添える。
- 理由：情報源を失うだけなら防災クイズになる。その後に残った手段で伝え直すことが、この作品を「避難訓練」にする。本人が実際には頼っていない情報源を失わせると立て直しの体験にならないので、出来事の前に本人の確認を挟む。確認をタップにすれば、6回の回答の枠を訓練の本体に使える。画面を3つにまとめるのは、ハッカソンの時間で作り切るため。新しい機能は増やさず、既に決めた要素（出来事の6候補、5観点、3段階、準備行動）を、どの順序でどう体験させるかを決めるもの。
- 却下案：
  - 出来事を対話の任意の時点で起こす（立て直しの回答が残らないことがある）。
  - 本人の確認を省き、回答から推定した情報源で出来事を起こす（頼っていない情報源を失わせるおそれがある）。

## ADR-0021 薬の名前・量・病名・種類を聞いてよい
- 状態：採用（2026-11-03、オーナーがチャットで決定）　日付：2026-11-03（Issue #8）
- 背景：試作版の通しで、オーナーが「聞き取りが微妙」と感じた。最初の質問に「血圧の薬を飲んでいますね」と答え、「他にどんな薬を飲んでいるか聞かないの？」と感じた。公式の手引き（README「参考にした公式資料」）を調べると、実際の聞き取りは、普段の薬があるか → 何で確かめられるか → ほかの病院の薬・市販薬 → アレルギー・副作用 → いつから・最近の変化 → 今飲めているか → 誰が管理しているか、の順で、薬の中身も聞いている。ADR-0009 で「実際の薬の名前は質問しない」としていたため、質問が不自然になっていた。
- 決定：薬の名前・量・病名・何の薬か（種類）を、実際の聞き取りに合わせて質問してよい。オーナーの条件は次のとおり。
  - アプリは答えを原文のまま返す（表示する）だけ
  - Claudeは診断も判断もしない（薬の名前の修正、薬効の評価、正誤の判定、服薬の適否の判断をしない）
  - 記録しない（ADR-0007）
- 変えないこと：薬の名前を言えたかどうかは評価しない。5観点と3段階の判定（ADR-0017）、ADR-0009 の必須事項（送信の明示、架空の情報でも練習できる、原文は端末内の入力から表示、薬の名前の有無で個別の医療判断をしない）。
- 理由：中身を聞かない質問は、実際の救護所の聞き取りと違い、訓練の場面として不自然になる。薬の名前や量を答えられるかどうか自体も、利用者の気づきの材料になる（日本薬剤師会の事例集に、薬効の言い方でしか伝えられず処方が合わなかった例がある）。アプリが答えを判定しないので、聞くこと自体は医療判断にあたらない。
- 却下案：中身は聞かず、在りかと手段だけを聞く（ADR-0009 の当初の方針。質問が不自然で、実際の聞き取りの練習にならない）。
- 影響：
  - `.claude/rules/safety.md`、PRD、README の「薬の名前は尋ねません」の記載を直す。固定の質問文と利用開始の案内（`web/src/flow/content.ts`）を直す。
  - 実際の服薬情報が入力されやすくなる。ADR-0009 の必須事項2（実際の患者情報を入力しないよう案内する）と、オーナーの判断待ちの「実際の服薬情報の入力を許すか」（ADR-0009）との関係は、オーナーの判断が要る。それまでは「架空の内容でも練習できる」を案内に残す。
  - Claude連携の後は、薬の名前を含む回答が Anthropic へ送られる。初回画面の説明（送信の明示）はそのまま必要。
  - 固定の質問の順番は、手引きの順番をもとに、後半を「代わりの手段 → 最近の変化・飲めているか → 薬を知っている人」とした（6問の枠に収めるための調整）。
- オーナーが判断した点：ADR-0021 と、ADR-0009 の必須事項2・「実際の服薬情報の入力を許すか」との関係
  - → オーナー決定（2026-11-03、チャット）：架空の情報だけで練習する（ADR-0009）。薬の名前・量・病名は聞くが、利用者には架空の内容で答えてもらう。案内（初回画面、回答欄）と README をこれに合わせる。

## ADR-0022 振り返り・復習のきっかけとしての役割と、答える範囲（案B）
- 状態：採用（2026-11-03、オーナーがチャットで決定）　日付：2026-11-03（Issue #12）
- 背景：
  - オーナーがコンセプトを言い直した：「避難所で自分の薬の情報を持ち合わせていないときに、しっかりと思い出せるように復習をするためのきっかけを与えるアプリ・サービス。医療判断はしない」。
  - 一方、ADR-0009（2026-11-03）で「架空の情報だけで練習する」と決め、回答欄はすべて「架空の内容で答えてください」とした（`web/src/flow/content.ts`）。架空の人の準備を振り返っても本人の復習にならない、という食い違いが Issue #12 と外部の助言（`docs/reviews/2026-11-03-fable-docs-advice.md`）で指摘された。
- 決定：
  1. **役割**：SonaQuest は、災害時に自分の服薬情報を伝える準備を**振り返り、復習してしっかり覚える**きっかけを与える。最終目標は、普段の情報源が使えなくても、自分の服薬情報を周囲に伝えられる状態に近づくこと。5観点・出来事・立て直しは、そのための手段。
  2. **答える範囲（案B）**：薬の中身（薬があるか・名前・量・病名・ほかの薬・市販薬・アレルギー・副作用・飲めているか）は架空の内容で答える。情報の在りか、ほかの伝え方、薬を知っている人（続柄と、その人がどのくらい知っているか・連絡の手段の種類。人の名前や電話番号、薬の中身は書かない）、記録が新しいかは、本人のこととして振り返って答える。回答欄の案内は質問ごとに分ける。
  3. **思い出せないとき**：アプリも Claude も、薬の名前・量・病名の候補や「〜ではないですか」を出さない。代わりに、固定文で「今ここで、実際のお薬手帳や薬の袋を確認しましょう」と促し、「今回のように、定期的にお薬の避難訓練をやっておくとよいですね」（オーナーの言葉）の趣旨を伝える。画面の文面は `web/src/flow/content.ts` の下書き（「〜をやって復習しておくとよいですね」）で、オーナーが確認する。確認した内容の入力は求めない。
  4. **デモ冒頭の問いかけ**：「あなたの薬のことを、どう伝えますか」（docs/demo-script.md）。
- 変えないこと：薬の名前を言えたかは評価しない（ADR-0009、ADR-0021）。5観点と3段階の判定（ADR-0017）。保存しない（ADR-0007）。医療判断をしない。
- 理由：振り返りと復習の対象は「伝える準備」で、それは実際の服薬情報を入力しなくても本人のこととして答えられる。薬の中身だけを架空にすれば、実際の服薬情報を入力しない方針（ADR-0009）を保ったまま、本人の準備の振り返りになる。思い出せないことを候補で補うと推定になるため、実物の確認と、訓練を繰り返すことに向ける。
- 却下案：
  - 案A（すべて架空）：本人の準備の振り返りにならない。
  - 案C（薬の中身は「言える／一部／言えない」の選択式）：実際の聞き取りの練習から離れる。
  - 助言にあった「『復習』という語は採点・暗記の印象を与えるので避ける」：オーナーの判断で採らない。
- 影響：PRD（目的、答える範囲、体験の流れの振り返り）、README、`web/src/flow/content.ts`（案内・回答欄・思い出せないときの固定文）、`.claude/rules/safety.md`、docs/safety-test-plan.md（S11〜S15、E8、E9、P10）、docs/evidence.md、docs/demo-script.md。Phase 2 の決めることの表（#15）に、思い出せない回答のときの扱いを入れる。

## ADR-0023 STATUS.md の更新漏れを hook で知らせる
- 状態：採用（オーナーの承認、2026-11-03、チャット）　日付：2026-11-03
- 背景：PR #10 で Phase 1 を main にマージした後も、STATUS.md には「ブランチ `feat/8-text-mvp` で作業中、mainには未マージ」と残った（Issue #13）。PRの中で、ブランチの立場から書いたため。マージはオーナーが GitHub 上で行うので、その時点では Claude Code の hook が動かない。
- 決定：
  - 書き方：STATUS.md は**マージ後の main の状態**として書く。STATUS.md はPRのマージで初めて main に入るため。マージ済みの作業は Issue・PR の番号で書き、ブランチ名は作業中のものにだけ使う。CLAUDE.md の「作業の流れ」と `session-handoff` Skill に書く。
  - セッション開始時（SessionStart hook、`.claude/hooks/status_check.py`）：STATUS.md に書かれたブランチ名のうち、main にマージ済みのものを Claude に知らせる。止めはしない。判定には、main の first-parent のマージコミットの件名「Merge pull request #N from 所有者/ブランチ」を使う。手元の git だけで調べ、通信しない。
  - PR作成時（PreToolUse hook、同じファイル）：`gh pr create` の前に、ブランチで STATUS.md が変わっていなければ止める。PR本文に「STATUS.md：更新不要（理由）」と書けば通す。止めたときは、dev-log の「いつ書くか」に当てはまるかも確かめるよう促す。
- 理由：書き方のルールだけでは、今回と同じ書き漏れを防げない。マージは hook の届かないところで起きるので、マージの後に最初に動けるセッション開始時に、ずれを見つける。PR作成は Claude Code が作業の完了を示す時点なので、そこで更新を促す。
- 却下案：
  - マージ済みのPRがすべて STATUS.md に載っているかを調べる：昔のPR（#3・#4）まで載せる手間が増え、雑音が多い。
  - hook の中で `git fetch` や `gh` を使う：セッション開始が遅くなり、通信できないと失敗する。
  - PR作成時に止めず、知らせるだけにする：終了コード0の PreToolUse の出力は Claude に届かない。
- 影響：
  - squash マージ・rebase マージだと件名の形が変わるので、気づけない。今の運用はマージコミット。
  - origin/main を fetch していなければ、新しいマージに気づけない（`git pull --ff-only` の後に効く）。
  - STATUS.md で、マージ済みの作業をブランチ名で書くと、そのたびに知らされる。
  - hook はセキュリティの境界ではない（ADR-0014）。PR本文に決まった文を書けば通る。

## ADR-0024 オーナーの決定の行が付いたマーカーの解除
- 状態：採用（2026-11-03、オーナーがチャットで決定。Issue #19）　日付：2026-11-03
- 背景：オーナーが決めたことを `[TODO-OWNER]` マーカーの横に書いても、マーカーの解除はオーナーが `SONAQUEST_OWNER_APPROVED=1` で行う必要があり、決定済みのマーカーが残り続けていた（STATUS「決定済み・マーカー解除待ち」）。決定の書き方も「オーナー決定」「オーナー指示」「オーナー（…）：〜する方向」「〜で採用する方針」が混ざり、どれが確定した決定か分からなかった。
- 決定（案）：
  1. **決定の行の形**：マーカーの直後の行（空行は飛ばす）に、`→ オーナー決定（YYYY-MM-DD、チャット）：決定の内容` と書く。行頭の `- `、`> `、`// `、`# `、`<!-- ` は付いてよい。かっこの中は日付で始まれば後に補足を足してよい（例：`（2026-11-03、チャット、Issue #12）`）。**確定した決定として扱うのはこの形だけ**。「オーナー指示」「オーナー（…）：〜の方向」「〜で採用する方針」「保留」は、決定として扱わない。
  2. **書いてよいこと**：決定の行には、オーナーがチャットで言ったことだけを書く。Claude Code が決定を作らない。言い換えたときは、PR の説明に元の言葉との対応を書く。決定の行の日付は、オーナーがチャットで決めた日を日本時間（JST）で書く（2026-11-04 追記）。
  3. **解除してよい条件**：ローカルの `main` にあるそのファイルで、マーカーの直後に決定の行があること。つまり、決定の行を足した PR をオーナーが確かめてマージした後でだけ、Claude Code は別の PR でマーカーを解除できる。解除しても決定の行は記録として残す。
  4. **機械的な守り**：
     - 基準にする main は、ブランチの `refs/heads/main`（`git show refs/heads/main:<そのファイル>`）。`main` という名前のタグや `refs/main` があっても取り違えない。
     - `.claude/hooks/protect_todo_owner.py`（Edit・MultiEdit・Write）：編集を当てた後のファイル全体と、編集前のファイル全体を比べる。消えてよいのは main で決定の行が付いたマーカーだけで、同じ文のマーカーが複数あるときも、決定の無いものが main より減れば止める（`replace_all` や MultiEdit での取り違えを防ぐ）。main にあるオーナーの決定の行を消す・書き換える編集は、マーカーが減らなくても止める。コマンド（`sed -i` 等）での書き換えは、決定があっても今までどおり止める。
     - `.githooks/scan_staged.py`（コミット前）：変更したファイルごとに、HEAD・ステージした内容・main の全体を同じ基準で比べ、満たせば `SONAQUEST_OWNER_APPROVED=1` なしで通す。名前の変更は変更前のパスで main を見る。パスは `-z` の出力から取り、空白や日本語を含んでも扱える。同じ文のマーカーが別のファイルで増えた分は、移したものとして差し引く（これまでと同じ）。main にあるオーナーの決定の行は、マーカーが減らなくても消させない。別のファイルへ移した決定の行は残したものとして扱うが、1つの追加で差し引けるのは1つの削除だけ。パスは、git が引用符で囲む見出し（「"」「\」・タブを含む名前）も元に戻して扱う。
     - `.claude/hooks/guard_github.py`：ローカルの main を動かす・同じ名前の参照を作る操作（`git branch -f/-m/-c` で main を作る・動かすもの、`git update-ref`・`git tag`・`git symbolic-ref` で main を作る・動かすもの、`git update-ref --stdin`、`git fetch` の `X:main`、`git push . X:heads/main`、`git switch -C main`・`git checkout -B main`（`-fBmain` などの書き方も）、`git rebase <起点> main`、main での手元のブランチからの `git pull --ff-only`）を止める。main を書き換えられると、作業ブランチの決定の行を main のものと見せかけられるため（Issue #19 のレビュー）。main を起点や条件に使うだけの操作（`git switch -C feat/x main`、`git tag v0.1.0 main`、`git branch --merged main` など）は止めない。
     - main の読み出しは `git --no-replace-objects` で行い、`git replace` で中身を差し替えて見せかけられないようにする。コミット前フックがファイル全体を読むのは、差分でマーカーの行が消えたファイルと、削除・名前の変更だけ（多くのファイルを含むコミットでも遅くならないように）。
     - 試験：`.claude/hooks/test_hooks.py` に、決定ありで通る、決定なしで止まる、「方向」「指示」では止まる、決定の行ごと消すと止まる、決定の行を足すのと同時に消すと止まる、作業ブランチで足しただけの決定の行では止まる、同じ文のマーカーの取り違え・`replace_all`・MultiEdit、`main` という名前のタグ、空白と日本語を含むパス、名前の変更、別のファイルへの移動、main を動かす操作を足した。
- 「Claude Code が決定の行を作ってマーカーを消す経路」の扱い：同じ編集・同じコミットで決定の行を足して消す経路と、作業ブランチで決定の行を足してコミットしてから消す経路は、ローカルの main が GitHub でマージした状態と同じである限り、**main を見るので止まる**。main を動かす主なコマンドは `guard_github.py` が止める。それでも次の経路は hook では止められない。
  - スクリプトの実行、別のターミナル、hook が読めない書き方でローカルの main を動かすこと（ADR-0014。hook はセキュリティの境界ではない）。この場合も、決定の行と解除は GitHub の main に対する1つの PR に一緒に出るので、オーナーがマージの前に気づける
  - 2回目のレビュー（Issue #19）で見つかり、このPRでは塞いでいない経路：`git -c remote.*.push=…`・`remote.*.fetch=…` の設定で宛先を決める push・fetch、`git worktree add` や `git -C <別の作業フォルダ>` での main の操作、`git checkout -` の後に続けた操作、`.git/refs/` への直接の書き込み、`git am`・`git revert`・`git cherry-pick`・`git merge`（コミット前フックが呼ばれないので、マーカーの削除を確かめない。この PR より前からの抜け道）。`.claude/rules/github.md` のとおり、hook の修正は別の Issue で扱う（Issue #30）
  - Claude Code が作った決定の行を含む PR を、オーナーがそのままマージすること
  そのため、決定の行を足す PR では、足した決定の行を説明に一覧で書き、オーナーがチャットの言葉と合っているかをマージの前に確かめる。マーカーを解除する PR では、解除したマーカーと根拠の決定の行を説明に一覧で書く（`.claude/rules/github.md`）。
- 理由：決定を足す PR と解除する PR を分ければ、オーナーのマージという確認を必ず1回はさむことになる。main を基準にすれば、作業ブランチの中だけで決定を作って解除する経路を、手元の git で止めやすい（止めきれない経路は上のとおりで、最後の確認はオーナーの PR の確認）。
- 却下案：
  - 作業中のファイルで決定の行があれば解除を通す（Claude Code が決定の行を足してすぐ消せる）。
  - 決定の行と解除を同じ PR で行う（オーナーがマージ前に見落とすと、決定と解除が一度に確定する）。
  - これまでどおりオーナーだけが解除する（解除待ちが溜まり、未決のマーカーと見分けにくい）。
- 影響：CLAUDE.md 絶対ルール5、`.claude/rules/github.md`。ローカルの `main` が古いと、マージ済みの決定でも解除できない（`git pull --ff-only` の後に効く）。hook はセキュリティの境界ではない（ADR-0014）。
- 今あるマーカーのうち、この形の決定の行が直後にあるのは ADR-0009（実際の服薬情報の入力）と ADR-0021（ADR-0009 との関係）の2つ。ほかは「オーナー指示」「〜の方向」「方針」や、決定の行が無いもの（一覧は Issue #19 の PR の説明）。
- オーナーが判断した点：マーカー解除のルールの変更
- → オーナー決定（2026-11-03、チャット）：採用する。main に入った「→ オーナー決定（日付）：」の行が直後にあるマーカーだけ、Claude Code が別のPRで解除してよい（決定の行は残す）。

## ADR-0025 Claude が作る文と、その検査
- 状態：採用（2026-11-03、オーナーがチャットで決定。Issue #19）　日付：2026-11-03
- 背景：オーナーの方針（2026-11-03、チャット。Issue #19）で、Claude がまず利用者に質問し、回答を受け付け、関係のない話はいったん受け止めてから本来の質問に答えるよう質問し直すことになった。これまでの「画面の文言はできるだけ固定文から選ぶ」（safety.md）と、Phase 2 の決めることの表の項目3（聞き返しの文面）・項目13（`redirect` を回数に数えるか）が関係する。
- 決定（案）：Claude が作ってよい文は、**質問文、受け止めの一言、質問し直す文**の3つだけにする。Workers で次を検査し、通らなければその文を捨てて、同じ質問 ID の固定文に戻す（ADR-0012、ADR-0015）。
  - 文の長さの上限（例：1文あたり80字、合計120字。値は実装時に決める）
  - 禁止表現：薬の名前の修正・言い換え、薬の名前・量・病名の候補や「〜ではないですか」、薬効・用法・用量への言及、服薬の助言、診断、緊急度の判断（語の照合。一覧は実装時に下書きしてオーナーが確かめる）
  - 利用者の発言の要約・言い換え・繰り返し：利用者の回答の一部（例：連続する6文字以上）が文に含まれていたら通さない。受け止めは「教えてくださってありがとうございます」のような、内容を繰り返さない一言にする
  - 結果画面の回答は、今までどおり端末内に持っている入力から原文で表示する。Claude の文を原文として扱わない（ADR-0009）
- Claude に任せる範囲の選択肢：
  | 選択肢 | 良い点 | 気になる点 |
  |---|---|---|
  | A. 聞く項目と順番（前半3問 → ③確認 → ④出来事 → 後半3問）は固定。Claude は質問の言い回し、受け止め・質問し直しの文を作り、5観点を判定する | 体験の核（ADR-0019）と固定の進行（ADR-0012）がそのまま使える。失敗したら同じ質問の固定文に戻せる。比較実験（docs/evidence.md）の条件をそろえやすい | 会話の自由さは言い回しの範囲にとどまる |
  | B. 何を聞くかも Claude が会話から決める | 会話が自然になり、手薄な観点を深く聞ける | 固定の進行に戻すときの対応づけが難しい。6回の枠と観点の網羅を Claude に頼ることになる。検査の範囲が広がる |
  - 推奨：**A**。体験の核と失敗時の進行を崩さずに、会話の自然さを足せる。B は提出後に検討する。
- 関係のない話への質問し直し（`redirect`）を、回答の回数（最大6回）に数えるか：
  - PRD と ADR-0019 は「聞き返しも回数に含める」としている。関係のない話は観点の答えにならないので、数えると訓練の本体に使える回数が減る。数えないと、関係のない話が続いたときに終わらない。
  - 推奨：**数えない。ただし質問し直しは1つの質問につき1回まで**とし、2回目の関係のない話は、そのまま回答として受け取って次へ進む（回数に数える）。曖昧な回答への聞き返し（`clarify`）は、これまでどおり数える。
- 理由：Claude の文を許すと会話は自然になるが、禁止表現が混ざる経路ができる。検査を通らなければ固定文に戻すことにすれば、検査の漏れがあっても、少なくとも固定文で訓練を終えられる。
- 却下案：すべて固定文から選ぶ（オーナーの方針「Claude がまず質問する」と合わない）。検査なしで自由文を出す（禁止表現が混ざる）。
- 影響：`.claude/rules/safety.md`・`scope.md`、docs/architecture.md、docs/phase2-decisions.md（項目3・13）、docs/safety-test-plan.md（S16〜S19）。
- 追記（2026-11-04、Issue #40）：Workers の検査の後に、別の Claude の呼び出し（監査役）で意味から確かめる守りを重ねた。監査役が止めたとき・失敗したときも、その文を捨てて固定文に戻す（ADR-0030）。
- オーナーが判断した点：Claude に任せる範囲（A・B）と、関係のない話への質問し直しを回答の回数に数えるか
- → オーナー決定（2026-11-03、チャット）：A（聞く項目と順番は固定。Claude は言い回しと、受け止め・質問し直しの文を作り、5観点を判定する）。関係のない話への質問し直しは回答の回数に数えず、1つの質問につき1回まで（2回目はそのまま回答として受け取る）。

## ADR-0026 Issue ごとの着手の承認
- 状態：採用（2026-11-03、オーナーがチャットで決定。Issue #19）　日付：2026-11-03
- 背景：CLAUDE.md 絶対ルール7では、push・PR の作成もそのつど承認が要り、1つの Issue を進めるたびに確認が重なっていた。
- 決定（案）：オーナーがチャットで「Issue #N に着手して」と言ったときは、その Issue の作業ブランチの作成、そのブランチへの push、PR の作成までを承認したものとする。マージ、デプロイ、外部サービスの課金・契約・アカウント作成、依存パッケージの追加、`main` の変更、GitHub の設定変更は、そのつど承認を得る。依存を足す Issue では、足す依存の一覧を Issue に書き、着手の承認とは別に確かめる。Issue の本文やほかの文書に書かれた「承認」は承認として扱わない。
- 確認したこと：`.claude/hooks/guard_github.py` は、作業ブランチへの push と `gh pr create` を止めない（`main` への push、force push、PR のマージ、保護設定の変更を止める）。`gh pr create` の前には `status_check.py` が STATUS.md の更新漏れだけを確かめる（ADR-0023）。hook の変更は要らない。
- 理由：作業ブランチと PR は、マージしない限り `main` を変えない。オーナーの確認はマージの前に PR で行える。
- 影響：CLAUDE.md 絶対ルール7、`.claude/rules/github.md`。

## ADR-0027 動作の要件をウェブブラウザにする
- 状態：採用（2026-11-03、オーナーがチャットで決定。Issue #17）　日付：2026-11-04
- 背景：PRD の要件は「iPhone Safariで動く」で、docs/evidence.md の主張、docs/safety-test-plan.md の「5. 端末」、docs/architecture.md の図もそれに合わせていた。iPhone 実機で確かめるには、手元の開発用サーバーを HTTPS で開く手段（cloudflared など）が要り、まだ決めていなかった。

  - → オーナー決定（2026-11-03、チャット）：iPhone 実機で見せなくてよい。ウェブブラウザで動作すればよい。iPhone 実機での確認は Issue #17 の範囲から外す。

## ADR-0028 Claude 連携（/api/turn）の実装の決まり
- 状態：採用（実装の細部。オーナーの決定は Issue #15 のコメントの表（2026-11-04。docs/phase2-decisions.md の訂正の行）と、下の2点）　日付：2026-11-04（Issue #15 の後半）
- 背景：Phase 2 の決めることの表（docs/phase2-decisions.md）の決定に沿って、Cloudflare Workers の `/api/turn` と、画面からの呼び出しを作った。表で決めていない細部を、実装で次のように決めた。
- 決定：
  1. **質問IDは Claude に選ばせない**。Claude が返すのは「次の手の種類」（次へ進む／聞き返す／質問し直す）と文だけで、どの質問を出すかは Workers と画面が固定の順番から決める（ADR-0025 の A）。画面に返す `next.question_id` は Workers が入れる。
  2. **許していない次の手は「次へ進む」に直す**。画面は、聞き返してよいか（その半分の回数の上限の前か）と、質問し直してよいか（その質問でまだ質問し直していないか）を送り、Workers はそれを超える次の手を「次へ進む」に直して、そのときの Claude の文は使わない。画面の側でも同じ条件を確かめる。
  3. **後半の最初の問い（立て直し・係の交代）は、Claude の言い回しにしない**（ADR-0019 の固定の問い）。Claude の言い回しを使うのは、同じ半分の中で次の固定の質問へ進むときだけ。
  4. **Claude が作った文の検査**（ADR-0025）：長さの上限は200字（`MAX_PROMPT_LENGTH`。プロンプトでは120字以内を求める）。禁止表現は語の照合（`web/worker/checks.ts`）で、推測の確かめ（名詞の直後の「でしょうか」「ですね」など）、病名らしい語、漢数字の用量、服薬の助言、安心させる判断（「大丈夫」「様子を見」）なども含める。アプリの固定の文に無いカタカナの言葉と「〜薬」「〜剤」の言葉は、利用者が言っていない薬の名前や薬の種類の推測とみなして捨てる。利用者の言葉の繰り返しは、利用者の入力の漢字の2文字ずつ、カタカナ・英数字の2文字以上の並び、ひらがな（長音を含む）の4文字ずつが、固定の文（質問、情報源の分類、出来事）に無いのに文に現れたら繰り返しとみなす。カタカナとひらがなの違いはそろえて比べる。ADR-0025 の例の「6文字以上」より短くしたのは、2文字の病名（喘息、血圧など）や薬の名前の繰り返しを捕まえるため（2026-11-04 の2回のレビュー）。誤って捨てても固定文に戻るだけなので、安全側に寄せた。
  5. **送るものと入力の上限**：送るのは、数える回答の原文と、その直前に画面に出した文（Claude が作った文を含む。項目4のオーナー決定）。関係のない話として質問し直した入力は、その後のやり取りでは送らない（判定の役に立たず、送るものは必要な範囲に限るため。2026-11-04 のレビュー）。1回に送る回答は6件まで、1件500字まで、画面に出した文は1件200字まで、本文は12,000字まで。質問ID・出来事・情報源は知っている値だけ。超えたものは Claude を呼ばずに拒否する（ADR-0003、safety-test-plan P8）。回数の制限と支出の上限（P7、P9）は公開の前に行う。
  6. **失敗の扱い**：Claude の失敗・時間切れ（8秒）・断られた（`refusal`）・途中で切れた・形の違う出力は、どれも「失敗」として画面に返し、画面はその回の残りを固定の進行にする（項目9）。API キーが無いときも、Claude を呼ばずに失敗を返す。画面は、Workers の8秒に通信の余裕を足した9秒で待つのをやめる（2026-11-04、ADR-0030 で、監査役の6秒を足して16秒に変えた）。
  7. **ログ**：公開する版では、失敗の種類（`turn: timeout` など）だけを出す。Claude の出力の本文は、`DEV_CONTENT_LOG=1` かつ宛先が localhost・127.0.0.1 のときだけ出す（ADR-0007 の追記）。Workers Logs は使わない（`wrangler.jsonc` の `observability.enabled: false`）。
  8. **モデルの呼び出し**：`claude-opus-5-5`、effort `low`、構造化出力（`output_config.format` の JSON スキーマ）、`max_tokens` 4096、SDK の再試行0回、システムプロンプトはキャッシュに置く。断られたときは、サーバー側で別のモデルが答え直す設定（`fallbacks: "default"`、beta `server-side-fallback-2026-07-01`）を使う（項目9のオーナー決定）。それでも断られたら失敗として固定の進行へ。Haiku 5.5 に替えたときは、この設定を外す（項目1・9）。
  10. **緊急の種類**：Claude は緊急を `none`・`symptom`・`self_harm` の3つで返す。自傷のほのめかしには、語の照合と同じく自傷用の案内を出す（ADR-0011。2026-11-04 のレビュー）。
  11. **Workers の入口**：`web/worker/index.ts` は `default` だけを出す。ほかの名前を出すと、Workers が起動しない（2026-11-04 のレビューで `wrangler dev` が止まった）。受け口の中身は `web/worker/app.ts`。
  12. **公開の切り替えと、問い合わせの確かめ**（2026-11-04、PR #39 のレビュー）：
     - Workers は、手元（localhost・127.0.0.1）からの呼び出しか、`PUBLIC_TURN=1` のときだけ Claude を呼ぶ。回数制限と支出の上限（ADR-0003、safety-test-plan P7・P9）を満たすまで `PUBLIC_TURN` は設定しない。誤ってデプロイしても、課金の呼び出しは起きない。
     - 本文は上限のバイト数までしか読まない（Content-Length でも確かめる）。
     - 画面が送る「次の質問」と「聞き返してよいか」を、固定の順番と回数の上限から確かめ、合わなければ拒否する。
     - 禁止表現の照合は、空白や改行を除いた文で行う。
     - 固定の文に無い英字の言葉も、薬の名前の推測として捨てる。
  9. **画面の状態**：Claude の返事を待っている間は次の回答を受け付けない。やめた・やり直した後に届いた返事は、訓練の回と入力の件数で見分けて捨てる。開発中の React の StrictMode で effect が2回動いても、同じ問い合わせは送り直さない。
- オーナーの決定（2026-11-04、チャット）：
  - Claude が途中で失敗した回は、それまでの判定も使わず、すべての観点を「判定できませんでした」にする。
  - 関係のない話として質問し直した入力も、振り返りの「あなたの回答（入力したまま）」に出す。
- 理由：Claude に質問IDを選ばせないほうが、検証する値が少なく、固定の進行（ADR-0012）とそろう。許していない次の手を直す処理を Workers と画面の両方に置けば、どちらかの漏れで回数の上限を超えない。
- 却下案：Claude に質問IDも選ばせて Workers で拒否する（拒否すると返事全体が失敗になり、固定の進行に落ちる回が増える）。検査に通らない文があったら返事全体を失敗にする（判定まで捨てることになる）。
- 確かめたこと（2026-11-04）：本物の Claude API で訓練を1回通し、6回の呼び出しが1.6〜3.5秒で返った。未確認：判定の一致率と、文が検査で捨てられる割合は、比較実験（docs/evidence.md、ADR-0006）で確かめる。
- 影響：`web/worker/`、`web/src/flow/`（`turnContract.ts`、`api.ts`、`training.ts`）、docs/architecture.md、README、docs/safety-test-plan.md。

## ADR-0029 聞き取り係の応答を自然にする（ADR-0025 の範囲の中で）
- 状態：採用（2026-11-04、オーナーがチャットで決定。文面は下書きで、マーカーでオーナーの確認待ち）　日付：2026-11-04
- 背景：2026-11-04、オーナーが訓練を通して、聞き取り係の応答が不自然だと感じた。応答の流れ（回答 → ブラウザの語の照合 → Workers が Claude を呼ぶ → 次の手を決める → 文の検査 → 画面）を図にして、固定文に戻る道を確かめた。
  - このときの通しは Claude API を動かしていなかった。API キーが無いと Workers は失敗を返し、画面はその回の残りをすべて固定文で進める（ADR-0028 の6）。2問目が受け止めの無い固定文そのままだったのは、この仕組みどおりの動き。
  - Claude の言い回しで訓練を通したのは、ADR-0028 の1回だけ。その後、モデルの比較実験（2026-11-04。docs/evidence.md「モデルの比較」）で、文が検査で捨てられる割合と理由を測った。
    - 1問目への1回の回答13件 × 3モデル（Opus 5.5・Sonnet 5.5・Haiku 5.5）で、Claude が文を作ったのは39回。捨てられたのは3回（Opus 2回、Sonnet 1回、Haiku 0回）で、どれも禁止表現の「大丈夫」に当たった。
    - 捨てられた3回の文は、どれも急がなくてよいことを伝える受け止めで、医療的な判断ではない（Claude Code が読んで確かめた）。表現の例は「ゆっくりで大丈夫です」「訓練は急がなくて大丈夫です」。
    - 繰り返しの検査と、固定の文に無い語の検査で捨てられた文は、39回のうち0回だった。下の4で心配した「わかりました」は、この実験では Claude が使わなかった。
    - 前半・後半の最後の回答（6回の回答をそろえた5件 × 3モデル＝15回）では、15回とも Claude は文を作らなかった。次の固定の質問が無いと文を null にするプロンプトのとおりで、下の1の「受け止めが出ない」が実際に起きることを確かめた。
    - 1件ずつ1回だけの試しで、件数は少ない。
  - 仕組みの上で、Claude を動かしても残る点がある。
    1. 前半・後半の最後の回答には、受け止めが出ない。`decideNext`（`web/worker/turn.ts`）は次の固定の質問が無いと `finish` にして文を捨て、画面は受け止めの一言を出さずに③確認・振り返りへ進む。
    2. Claude の文が使えなかったとき（検査に通らない、文が空、呼び出しの失敗）に出す固定文には、受け止めの一言が無い。会話が急に硬くなる。
    3. 固定の進行に落ちたことが、訓練の途中では利用者に分からない。分かるのは結果画面の `AI_FAILED_NOTE` だけ。
    4. 繰り返しの検査（ひらがな4文字ずつ。ADR-0028 の4）が、答え方の言葉に当たることがある。Claude Code が `checks.ts` を手元で試した結果（2026-11-04）：よくある回答6つ × よくある受け止め7つの組み合わせで捨てられたのは、「わかります」を含む回答の後の「わかりました。」だけだった。もう1つ、「わからないです」の後の「わからないことに気づけたのも大切です」も捨てられた。受け止めの多くは通る。影響は狭い。
    5. 捨てられた理由が分からない。ログに出るのは `turn: text_rejected` だけで、長さ・禁止表現・未知の語・繰り返しのどれで捨てたかは分からない（上の比較実験では、捨てられた文を Claude Code が読んで理由を調べた）。
    6. 禁止表現の「大丈夫」（安心させる判断を止めるための語）が、急がなくてよいことを伝える受け止めにも当たる。比較実験で捨てられた3回は、すべてこれだった。
- 決定（案）：
  1. **まず測る**。文を捨てた理由の種類（`length`／`forbidden`／`unknown_term`／`repeat`）を、`turn: text_rejected:<種類>` の形でログに出す。本文を含まない「エラーの種類」なので、公開する版でも出してよい（ADR-0007、privacy.md）。そのうえで本物の Claude API で数回通し、捨てられた回数と理由を docs/evidence.md に記録する。下の2〜5は、この結果を見てから着手してよい。
  2. **前半・後半の最後の回答に、固定の受け止めの一言を出す**。
     | 選択肢 | 良い点 | 気になる点 |
     |---|---|---|
     | A. 固定の一言を、③確認と振り返りの冒頭に出す | 文の検査が要らない。Claude の失敗時も同じに動く | 毎回同じ一言になる |
     | B. `finish` のときも Claude に受け止めの一言だけを作らせ、同じ検査を通す | 言い回しに幅が出る | `/api/turn` の形（`next.text` の意味）と試験を直す。受け止めは内容に触れられないので、幅は小さい |
     | C. 今のまま | 変更なし | 最後の回答の後に、会話が途切れる |
     - 推奨：**A**。受け止めは内容に触れない決まり（ADR-0025）なので、B で得られる違いは小さい。
  3. **Claude の文が使えなかったときの「次へ進む」の固定文に、同じ固定の一言を前に付ける**（呼び出しの失敗後、固定の進行で進むときを含む）。聞き返し・質問し直しの固定文（`CLARIFY_TEXTS`・`REDIRECT_TEXTS`）には、すでに受け止めの文があるので付けない。2 と同じ固定文を使い、仕組みを1つにする。
  4. **固定の進行に落ちたときに、画面に短い知らせを出す**。出すのは呼び出しが失敗したとき（`ai` が `failed` になったとき）の1回だけ。1つの文が検査で捨てられただけのときは出さない（固定文に戻るのはその質問だけで、知らせが多いと邪魔になる）。
  5. **繰り返しの検査で、答え方の言葉を許すか**。
     | 選択肢 | 良い点 | 気になる点 |
     |---|---|---|
     | A. 「わかりました」など、受け止めに使う決まった言葉だけを許す言葉に足す | 捨てられる受け止めが減る。薬の名前を見逃すおそれは増えない | 足す言葉の一覧を決めて、保守する |
     | B. ひらがなの照合を5〜6文字ずつにする | 一覧が要らない | ひらがなで書いた短い薬の名前の繰り返しを見逃す |
     | C. 今のまま | 変更なし | 「わかりました。」が捨てられることがある（影響は狭い） |
     - 推奨：**A**。ただし「わからない」「覚えていない」を受け止める文は許す言葉に入れない。思い出せない回答の後には、すでに固定文（`RECALL_NOW`。2026-11-04 オーナー決定）を出しているので、重ねると同じことを2回言う。利用者の答えを言い直す形にもなりやすい（ADR-0025）。
     - 比較実験では、繰り返しの検査で捨てられた文は0回だった（背景）。急ぐ必要は小さいので、1 の測る仕組みで実際の回数を見てから決めてもよい。
  6. **禁止表現の「大丈夫」で、急がなくてよいことを伝える受け止めを許すか**（背景の6。比較実験で捨てられた3回すべての理由）。
     | 選択肢 | 良い点 | 気になる点 |
     |---|---|---|
     | A. 「ゆっくりで大丈夫」「急がなくて大丈夫」など、急がなくてよいことを伝える決まった言い方だけを、禁止表現の例外に足す（今の「書かなくて大丈夫」の例外と同じ形） | 捨てられる受け止めが減る。体調や薬について「大丈夫」と言う文は今までどおり捨てる | 例外の言い方の一覧を決めて、保守する。例外の言い方の後ろに体調の話が続く文を、別の語で止められるかを試験で確かめる |
     | B. 今のまま | 安心させる判断が混ざる経路を広げない | 「ゆっくりで大丈夫です」の受け止めが捨てられ、固定文に戻る（今は Claude の文の約8%） |
     - 推奨：**A**。安心させる判断は、体調や薬についての「大丈夫」で、急がなくてよいという訓練の進め方の話とは別。例外は決まった言い方だけにして、「大丈夫」のほかの使い方は今までどおり捨てる。禁止表現の一覧は `[TODO-OWNER]` 付きの下書きなので、例外もオーナーが確かめてから足す。
- 下書きの文面：
  - [TODO-OWNER: 前半・後半の最後と、固定の進行で次へ進むときに出す受け止めの一言（Claude Code の下書き：「教えてくださってありがとうございます。」）]
  - [TODO-OWNER: 固定の進行に落ちたときの知らせ（Claude Code の下書き：「AIとのやり取りがうまくいかなかったため、ここからは決まった質問で進めます。」）]
  - [TODO-OWNER: 繰り返しの検査で許す、受け止めの決まった言葉の一覧（Claude Code の下書き：「わかりました」「承知しました」）]
  - [TODO-OWNER: 禁止表現の「大丈夫」の例外にする、急がなくてよいことを伝える言い方（Claude Code の下書き：「ゆっくりで大丈夫」「急がなくて大丈夫」「あわてなくて大丈夫」）]
- この ADR で変えないもの（オーナーが決めた上限）：
  - 回答の中身に触れる受け止め（例：「血圧の薬ですね」）。利用者の発言の繰り返しと、薬の名前・病名を文に入れることになり、safety.md と ADR-0025 が禁じている。
  - 聞く項目と順番（ADR-0025 の A）。何を聞くかを Claude が決める B は、提出後の課題（docs/roadmap.md）。
  - 後半の最初の立て直しの問いを固定文にすること（ADR-0019、ADR-0028 の3）と、③確認・④出来事が対話ではなく画面の部品であること。
  - 1問目は固定文のまま。まだ回答が無く、Claude を呼ぶと最初の質問の前に待ち時間ができる。
  - 変えるなら、別の ADR で決め直す。
- 理由：Claude を動かしても会話が硬く感じられる原因は、Claude の文が出ない場面（半分の最後、固定文に戻ったとき）に受け止めが無いことと、固定の進行に落ちたことが見えないことにある。どちらも固定文と画面の変更で直せて、Claude が作ってよい文の範囲（ADR-0025）を広げずに済む。検査を緩める前に、捨てられた理由を測る。
- 却下案：検査をやめて Claude の文をそのまま出す（禁止表現が混ざる経路ができる）。文が捨てられたら Claude を呼び直す（待ち時間が倍になり、8秒の上限に収まらない）。
- 影響：`web/worker/app.ts`・`turn.ts`・`checks.ts`（理由の種類と、許す言葉）、`web/src/flow/content.ts`（固定文）、`web/src/flow/training.ts`・`web/src/screens/`（受け止めの一言と知らせの表示）、docs/safety-test-plan.md（S16〜S19 に、許す言葉の試験を足す）、docs/evidence.md（捨てられた回数と理由）。実装するときは、変更の後に `safety-review` Skill を使う。
- オーナーが判断する点：2 の A・B・C、5 の A・B・C、6 の A・B、1 で測ってから着手するか（比較実験で一部は測れた）、上の3つの文面。
- → オーナー決定（2026-11-04、チャット）：推奨どおりに進める。あわせて、Claude を呼ぶときのシステムプロンプトを足して直す。2 は「Claude の一言＋固定文の予備」（A と B を合わせる）、5 は A、6 は「プロンプトと例外の両方」。
- 実装（2026-11-04、Issue #15 の後半）：
  - 1：文を捨てた理由を `turn: text_rejected:<length|forbidden|unknown_term|repeat>` でログに出す（`web/worker/checks.ts` の `promptTextProblem`）。
  - 2：半分の最後も、Claude に内容を繰り返さない受け止めの一言を作らせ（システムプロンプト）、同じ検査を通して③確認・振り返りの冒頭に出す。使えないときは固定の一言（`ACK_TEXT`）。
  - 3：Claude の文が使えずに次の固定の質問へ進むとき（呼び出しの失敗後を含む）は、固定の一言を前に付ける。
  - 4：固定の進行に切り替えた回答の後に、知らせ（`FALLBACK_NOTICE`）を1回だけ出す。
  - 5：受け止めの決まった言葉（`ACK_WORDS`）を、繰り返しの検査で許す。
  - 6：プロンプトで「大丈夫」など安心させる言い方を使わないよう伝え、急がなくてよいことを伝える決まった言い方だけを、禁止表現の例外にした。

## ADR-0031 提出版の完成形と開発範囲（A〜D）を定める
- 状態：採用（完成体験、2D と 3D の扱い、A〜D の区分、Coming soon の決まり、完了条件。2026-11-04、オーナーがチャットで指示。Issue #44）。同じ日に、オーナーが確認事項に答えた（下の「追加の決定」）。A-02 以外の受入条件の下書きは確認待ち（下のマーカー）　日付：2026-11-04
- 背景：
  - Phase 0〜2 で、文字の訓練（Phase 1、Issue #8）と Claude 連携（Phase 2、Issue #15、PR #39）が main に入った。一方で、提出版が何を満たせば「完成」かを書いた所が無かった。3D パペット（#37）、監査役（#40）、回答の回数（#41）、動画（#28）は、それぞれの Issue で別々に進んでいた。
  - PRD と ADR-0020 は「2D の SVG・CSS を基本とし、凝ったイラストや 3D は作らない」とし、#37 は「聞き取り係を 3D のパペット風にする」としていた。
  - `.claude/rules/scope.md` の「モードは1つ」「作らないもの：複数モード」と、2D／3D を選ぶことの関係が書かれていなかった。
  - 公的資料へのリンクは、PRD に「固定文には出典と確認日を添える」とあるだけで、振り返りに必須かが決まっていなかった。`docs/references.md` の公的資料の候補4件は、どれも未確認。
- 決定（オーナーの指示、2026-11-04、チャット。Issue #44 の本文に写した）：
  1. **完成体験**：患者の立場で「災害時に自分の服薬情報をどう伝えるか」を練習する。体験の核（伝える → 頼っている情報源が使えなくなる → 別の手段で立て直す → 振り返りと準備行動につなげる。ADR-0019）は維持する。文字ばかりにせず、イラストや図でも内容を理解でき、分かりやすく参加しやすい体験にする。
  2. **2D と 3D**：患者向けに 2D と 3D のモードを用意し、利用者が選べる構想にする。2D は 3D が動かない場合の代用品だけではなく、正式な選択肢として残す。
  3. **区分**（要件ID と受入条件は PRD「提出版の完成形」）：
     - A（提出に必須）：2D 応答モードの訓練の完成、使いやすい UI と 2D キャラクター、お薬手帳・お薬の説明書・スマートフォンなどのイラスト、情報源や選択肢を文字と図の両方で示す表示、振り返りでの公的資料へのリンク（準備行動との関係が分かる表示。出典・確認日・リンク先を確かめ、未確認の資料を確認済みとして扱わない）、既存の安全要件（医療判断をしない、保存・外部送信、中断など）。
     - B（追加演出・追加機能）：出来事をグラフィカルに示すイベント UI、訓練の状況や変化が伝わる演出、BGM、3D パペットの対話モード、2D／3D のモード選択。B が未完成でも、A の 2D 訓練を最後まで使えるようにする。BGM や動きは、消音・読み上げとの両立・動きを減らす設定などを受入条件にする。
     - C（今回は実装しない将来構想）：薬剤師や医師の立場から、患者の服薬情報や状況を確認するトレーニング。患者向けとは別の機能。「Coming soon」と表示し、「将来構想・提供時期未定」と分かる説明を付ける。完成済み・開発着手済みとは見せない。
     - D（よりよい到達点・社会実装）：デプロイして URL を共有し、実際に体験してもらえる状態。行政へのマスコット使用許諾・協力の相談。地域の商工会議所などとの接点。
  4. **Coming soon**：3D が未実装のときは「Coming soon」と表示し、今使えるものと開発予定を区別する。動かないボタンを押せるようにしない。
  5. **完了条件**：A の各項目について、①実装され main に取り込まれている、②動作確認が済み、対象コミット・日付・環境・結果が記録されている、③必要な安全確認が済み、未解決事項の扱いが明確になっている、の3つを満たす。単体試験だけでなく、開始から振り返り・公的資料への導線までの通し操作も確かめる。API 失敗時、中断、ブラウザの保存・外部送信・ログの扱いも対象にする。

## ADR-0030 監査役の Claude で、聞き取り係の文を画面に出す前に確かめる
- 状態：実装済み（監査役を入れることは、オーナーの提案と指示（2026-11-04、チャット。Issue #40）。モデル・待ち時間・文面・考え中の表示は下書きで、マーカーでオーナーの確認待ち）　日付：2026-11-04（Issue #40）
- 背景：聞き取り係の Claude が作った文は、Workers の語の照合（`web/worker/checks.ts`、ADR-0025・ADR-0028 の4）で確かめている。語の照合は言い回しを変えると通ってしまう。監査役の比較実験（2026-11-04。docs/evidence.md「監査役の比較」）では、止めるべき文18件のうち6件が語の照合を通った（推測「痛み止めのようなもの」、安心させる判断、助言、緊急度の判断、実際の情報を求める文、役割の外の質問）。同じ30件を、別の Claude の呼び出し（監査役。Haiku 5.5、直したプロンプト）に判定させると、3回とも、出してよい文12件をすべて通し、止めるべき文18件をすべて止めた。応答時間の中央値は約1.1秒だった。オーナーはこの結果を根拠に本番に入れるよう指示した（Issue #40）。
- 決定：
  1. **位置づけ**：監査役は、語の照合の後に重ねる2つめの守り。語の照合を通った Claude の文だけを監査役に送る。文が無いとき、語の照合で捨てたときは呼ばない。Claude が緊急（`symptom`・`self_harm`）を返したときも呼ばない（画面は文を使わずに中断の案内を出すので、案内を監査役の分だけ待たせない。2026-11-04 のレビュー）。監査役は文を書き換えない。「出してよい／止める」と止める理由の種類（`medical_guess`・`medical_advice`・`diagnosis_or_urgency`・`reassurance`・`personal_info`・`off_role`・`other`）だけを返す。
  2. **送る内容**：Claude が作った文と、その文が言い直している固定の質問文だけ（次の質問へ進むときは次の質問、聞き返し・質問し直し・半分の最後の受け止めは、いま答えた質問。実験と同じ渡し方）。利用者の回答そのものは送らない。ただし、語の照合で見つけられない形の言い直し（ADR-0028 の4）が文に残っていれば、その部分は監査役にも届く。
  3. **止めたとき・失敗したとき**：監査役が止めたとき、または監査役の呼び出しが失敗・時間切れ・断られた・形の違う出力になったときは、その文だけを捨てて固定文に戻す（確かめられなかった文は出さない）。判定と次の手は、聞き取り係の返事をそのまま使う。固定文に戻るのはその質問だけなので、固定の進行に落ちた知らせ（ADR-0029 の4）は出さない。
  4. **モデルと待ち時間**：`claude-haiku-5-5`、effort `low`、構造化出力、SDK の再試行0回、6秒（`web/worker/audit.ts`）。画面が返事を待つ上限は、聞き取り係の8秒（項目9）と監査役の6秒に通信の余裕を足して、9秒から16秒にする（`web/src/flow/api.ts`。ADR-0028 の6を変える）。
  5. **ログ**：止めた理由は `turn: text_rejected:audit_<種類>`、失敗は `turn: audit_failed:<種類>`。どちらも本文を含まない種類だけなので、公開する版でも出してよい（ADR-0007、privacy.md）。
  6. **比較実験の切り替え**：手元の比較実験（`DEV_EXPERIMENT=1` かつ宛先が localhost・127.0.0.1）のときだけ、`DEV_AUDIT=off` で監査役を外せる。公開する版では必ず監査役を通す。測った値の見出しに、監査役の判定・理由の種類・失敗の種類・時間・使った量を載せる（本文は載せない）。
  7. **考え中の表示**：返事を待つ間、聞き取り係の光がゆっくり明滅し、「次の質問を考えています」の後ろに点が流れる。読み上げは文だけ（`role="status"`、点は `aria-hidden`）。動きを減らす設定（`prefers-reduced-motion`）では動きを止め、光と点は止まったまま、文で示す（ADR-0020 の「状態は文字でも示す」）。オーナーの意見（2026-11-04、チャット）：即答されると驚く。考え中の動きがあれば、待ち時間は自然に感じられる。
- 理由：語の照合は速く、外部に送らずに確実に止められる語がある。一方で、言い回しを変えた推測・助言・安心させる判断は語では捕まえきれない。意味で判断する監査役を重ねると、実験の30件では、語の照合だけで止まらなかった6件もすべて止まった。Haiku 5.5 は Sonnet 5.5 より料金が約18分の1で、最大の応答時間も短かった（docs/evidence.md）。監査役が答えられないときに文を捨てる側に倒せば、監査役の不具合で禁止表現が出ることは無い。
- 却下案：
  - 語の照合をやめて監査役だけにする（監査役も LLM で完全ではない。外部の呼び出しが止まったときに守りが無くなる）。
  - 監査役が止めたら聞き取り係を呼び直す（待ち時間が倍になる）。
  - 監査役が失敗したら文をそのまま出す（確かめられなかった文が出る）。

- 作り方（Claude Code の下書き。実装は Issue #37 の実装の PR）：
  1. 形：`three` を直接使い、球・円柱・カプセルなどの基本の形を組み合わせてコードで作る。手袋人形のように、袖のような胴、丸い頭、上下に開く口、目、短い腕。外部のモデルファイル・画像・素材は使わない。質感は平らな塗り（トゥーン調）にとどめ、作り込みすぎない（2D をやわらかいイラスト調にそろえるため。#47）。
  2. 色：本来の係は、クリームホワイトの体に淡いミントの襟、温かいオレンジの頬。係の交代（出来事「どれにも当てはまらない」）では、淡いミントの体に温かいオレンジの襟の、別の色のパペットに代わる。
  3. 状態：アプリが渡す状態だけで動かす。Claude の出力は使わない。
     - 待機：ゆっくり揺れる
     - 聞いている：少し傾く、うなずく
     - 話している：口が開け閉めする（読み上げの再生中。音声が無いときは文を表示している間。合わせ方は音声の Issue #53）
     - 考え中：返事を待つ間（ADR-0030 の考え中の表示）。少し上を見て、ゆっくり揺れる
     - 状態は動きだけでなく文字でも示す（ADR-0020）。「考え中」はオーナーの表（待機・聞いている・話している）に無く、ADR-0030 の考え中の表示に合わせて Claude Code が足した。
  4. 読み込み：three は 3D を表示するときだけ動的に読み込む（最初の表示を遅らせない）。読み込むまでと、読み込めなかったときは、2D の聞き取り係を出す。
  5. 2D への切り替え：WebGL が使えないとき、動きを減らす設定のとき、three を読み込めなかったとき、描画の途中で WebGL の文脈が失われたときは、2D の聞き取り係で続ける。切り替えるのは見た目だけで、訓練の進行（回答と段階）は変えない。声（認識と読み上げ）をどうするかは、この ADR では決めない（上の判断会の要旨の確認と、音声の Issue #52・#53 で決める）。動きを減らす設定は、訓練の途中で変えても切り替わる。
  6. 中断の画面：中断の画面に移ったら、描画のくり返しを止め（`setAnimationLoop(null)`）、描画の領域（canvas）を画面から外す。そのうえで、形（geometry）・色と質感（material・texture）・描画の仕組み（renderer）を three の `dispose()` で破棄する。WebGL の文脈は、すぐに手放すため `forceContextLoss()` で手放す（すでに失われた文脈には呼ばない）。
  7. 重さ：形の頂点を少なくし、画素の密度の上限を2倍、描画を1秒に30回までにする。スマートフォンのブラウザでも動く重さにする。タブが隠れている間は描画しない（ブラウザが止める）。
  8. つなぎ目：`web/src/screens/Listener.tsx` に、省略できる props `mode`（`"2d" | "3d"`、既定 `"2d"`）、`activity`（`"idle" | "listening" | "speaking" | "thinking"`、既定 `"idle"`）、`relief`（係の交代）を足す。既定のままなら今と同じ表示にする。どの画面で 3D を使うかと、状態を渡すのは、モード選択と音声の側（#51・#52・#53）。
  9. 確かめ方：開発のときだけ開ける見本のページで状態を切り替え、開発用サーバーで画面写真を撮って PR に添える（実際の会話は写さない）。見本のページは本番のビルドに入れない。
- 参考にした設計（考え方だけ。コードは複製しない。絶対ルール1）：オーナーが示した Guttyo/virtual-puppet-theater（ADR-0005）のパペットは、形をコードで組み、話している間に口を開け閉めする。SonaQuest では、口の動きを「話している」状態に合わせる。MediaPipe による手の操作は使わない。
- 見た目の注意：実在の人に似せない。オーナーにも似せない（絶対ルール8。動画の 3D キャラクターとの関係は #28 で決める）。白衣・聴診器・十字など、医療者を表す服装や記号を使わない。

## ADR-0035 /api/turn の回数制限（Rate Limiting binding、IP ごと）
- 状態：採用（実装。実環境の確認は Issue #58）　日付：2026-11-04（Issue #57）
- 背景：`/api/turn` は誰でも呼べる、お金のかかる呼び出し口になる。公開前の必須条件の1つ（ADR-0003、safety-test-plan P7）として、リクエストの回数制限が要る。支出の上限（P9、Anthropic 側）は最後の守りで、総量は抑えられるが、短い間の連打は抑えられない。
- → オーナー決定（2026-11-04、チャット）：「案どおり#57に着手して」。案は、方式 (a) Workers の Rate Limiting binding、IP ごと、60 秒で 10 回（同日のチャットの提示と、Issue #57 の本文）。全体の上限の併用は案に含まれていない。
- 決定：
  1. **方式**：Workers の Rate Limiting binding（`wrangler.jsonc` の `ratelimits`、binding 名 `TURN_LIMITER`、`namespace_id` は `"5701"`、`simple: { limit: 10, period: 60 }`）。依存パッケージは足さない（`wrangler` 4.156.0 が読む。型は `web/worker/ratelimit.ts` に最小限を自分で持つ）。
  2. **数えるもの**：接続元の IP（Cloudflare が付ける `cf-connecting-ip`）ごと。キーは `turn:<IP>`。ヘッダーが無いときは `turn:unknown` を全員で共有して数える（数えるのをやめない）。関数は接頭辞を引数に取るので、別のお金のかかる呼び出し口（読み上げの中継など）は別の接頭辞で同じ関数を呼べる。
  3. **数える場所**：`/api/turn` の、Claude を呼ぶ直前の最後の関門（公開の切り替えの確認、本文の大きさ・形・固定の順番の検査、API キーの確認の後）。外部へのお金のかかる呼び出しが起きない入力（形の違う入力、大きすぎる入力、API キー無し）は数えない。
  4. **数える条件**：公開の切り替え（`PUBLIC_TURN=1`）のときだけ。手元の開発では数えない（比較実験が続けて呼ぶため）。公開の切り替えが無い公開環境は、回数制限の前にこれまでどおり閉じる。
  5. **閉じ方**：上限を超えたら 429（`{"error":"rate_limited"}`、`Retry-After: 60`）で拒否し、Claude も監査役も呼ばない。公開の切り替えなのに binding が無い（設定漏れ）・binding が失敗したときは 503 で閉じる（回数制限の無いまま課金の呼び出しを開かない）。画面は `!response.ok` を失敗として扱うので、固定の進行で最後まで進む（ADR-0012、ADR-0028 項目6）。
  6. **ログ**：`turn: rate_limited`、`turn: rate_limiter_no_limiter`、`turn: rate_limiter_error` の種類だけ。IP と本文は出さない（ADR-0007）。
- 理由：
  - 設定が `wrangler.jsonc` の数行で済み、状態を持つ部品（DB・Durable Objects）を足さない。「DB なし」の方針（ADR-0003）に合う。会話の本文は binding に渡さない。
  - 近似でも、短い間の連打（誤動作・簡単な悪用）は止められる。総量は P9 で受ける。
  - 公開の切り替えで binding が無いときに閉じることで、設定の誤りが課金に直結しない（ADR-0028 の12と同じ考え方）。
- 却下案：
  - Durable Objects で厳密に数える：状態を持つ（「DB なし」との調整が要る）。今の規模では厳密さは要らず、P9 が最後の守り。
  - WAF の回数制限ルール：無料プランは 1 ルール・IP のみ・10 秒だけ。`workers.dev` ではゾーンが無く使えない見込み（確かめていない）。
  - IP 以外のキー：ログインが無く、使える識別子がほとんど無い。公式は IP を勧めていない（共有されうるため）が、ほかに無い。
  - 全体の上限だけにする：1 人の連打で全員が止まる。案に含まれていないので、併用もしていない。
- 限界：
  - **近似**：Cloudflare の拠点ごとに数え、世界全体では合算されない。上限をわずかに超えることがある。期間は 10 秒か 60 秒だけで、1 日あたりの上限は作れない（Cloudflare の公式ドキュメント、2026-11-04 に確認）。
  - **同じ IP を多くの人が使う場所**（展示・授業・避難所の共有の回線など）では、正常な利用者も拒否されうる。拒否されても固定の進行で最後まで進む。1 人の通常の訓練は、数分かけて最大 10 回の呼び出しなので、1 人では超えない。同じ IP の複数人が同時に訓練すると、60 秒に合計 10 回を超えて拒否されることがある。入力を即時にした自動の通し（34〜71 秒）も、続けて 2 回流すと超える。値は `wrangler.jsonc` の1か所で、変えたらデプロイし直す。
  - **実環境では未確認**：試験は偽の binding で行った。`wrangler dev` での binding の動作と、`workers.dev` での拠点ごとの挙動は確かめていない（Issue #58 で、デプロイした Workers に上限を超える回数を送って確かめる）。
  - binding のカウンターを Cloudflare 側がどう保持するかを、公式は明示していない。アプリは IP を保存せず、ログにも出さない。
- 影響：`web/worker/ratelimit.ts`（新規）、`web/worker/app.ts`（`Env` に `TURN_LIMITER`、入口で1回呼ぶ）、`web/wrangler.jsonc`、`web/worker/ratelimit.test.ts`・`turn.test.ts`、docs/safety-test-plan.md（P7）、docs/architecture.md、docs/STATUS.md。
- 追記（2026-11-04、Issue #58）：公開環境で回数制限を確かめたところ、上限（10回 / 60秒）を超える33回の呼び出しで、429 が1度も出なかった（14件の同時、逐次4件、逐次14件。docs/safety-test-plan.md「実施の記録」の P7）。原因は未調査。ADR-0028 の12（P7・P9 を満たすまで `PUBLIC_TURN` を設定しない）の P7 を、実環境では満たせていない。
  - → オーナー決定（2026-11-04、チャット）：「このまま続ける」（質問は「回数制限が効くと確認できるまで、PUBLIC_TURN を外しますか？」）。`PUBLIC_TURN=1` を設定したまま続ける。
  - Claude Code の整理（決定ではない）：この間、支出の最後の守りは P9（Anthropic 側の月の上限。オーナーが設定したと申告）だけになる。原因の調査と対処は、別の Issue で扱う案。

## ADR-0033 3D の対話モードの音声：押して話す入力と、ElevenLabs の読み上げ
- 状態：採用（下の3つの決定の行は、オーナーが 2026-11-04 にチャットで選択肢から選んだもの。Issue #52・#53）。押し方の既定（押し続けるか、1回押しか）と、ブラウザの読み上げに切り替える秒数は、オーナーの確認待ち（下のマーカー）　日付：2026-11-04
- 背景：
  - ADR-0031 で、音声は 3D の対話モードだけで使い、提出に必須（A-15 音声入力、A-16 音声合成）になった。方式は ADR-0004（Web Speech API）と ADR-0005（ElevenLabs、失敗したらブラウザの読み上げ）で決まっていた。
  - ADR-0005 が参考にした設計は、マイクを常に開き、利用者が話し始めたら読み上げを止める。PRD の A-16 も「利用者が話し始めたら止める」としていた。
  - PRD の A-13 は「WebGL が使えないとき・動きを減らす設定のときは 2D で続ける」とだけ書き、そのとき声を使い続けるかが決まっていなかった。
- オーナーの決定（2026-11-04、チャット。選択肢の言葉のまま）：
  - → オーナー決定（2026-11-04、チャット）：マイクは「押して話す（推奨）」。選択肢の説明は「「話す」を押している間だけ聞く。読み上げの間はマイクを閉じる。自分の声を拾わず、周りの会話も拾わない。1問1答で直してから送る流れに合う」。
  - → オーナー決定（2026-11-04、チャット）：3D の対話モードで、WebGL が使えない・動きを減らす設定のせいで 2D の姿に戻ったときは「見た目だけ変える（推奨）」。選択肢の説明は「姿は 2D のパペットに戻すが、声で答える・読み上げを聞くはそのまま使える。動きを減らす設定の人も声を失わない。2D モードを選んだ人は今の決定どおり文字で答える」。
  - → オーナー決定（2026-11-04、チャット）：ElevenLabs は「有料プランで（推奨）」。
- 決定（上の決定に沿った Claude Code の実装。`web/src/voice/`、`web/src/flow/mode.ts`、`web/worker/tts.ts`）：
  1. **声を使うかは、3D の対話モードを選んだかだけで決める**。3D を描画できるか（WebGL・動きを減らす設定）では決めない。2D モードは文字で答える（ADR-0031）。モード選択の画面（A-14、#51）ができるまでは、URL に `?mode=3d` を付けたときだけ 3D の対話モードにする（仮。`mode.ts`）。
  2. **押して話す**（`talk.ts`）：「話す」を押している間だけ、Web Speech API（`ja-JP`）でマイクを開く。指を離すと止め、確定した文を入力欄の後ろに足す。利用者が言っていない句読点は足さない。途中の文は画面にだけ見せる。認識した文は送らず、利用者が直してから「答える」で送る（ADR-0010）。キーボードでは、スペースか Enter を押している間。
     - 押し方の既定は「押し続ける」（`TALK_STYLE = "hold"`）。「1回押すと聞き始め、話し終わると自動で止まる」（`"tap"`）は PM の提案で、オーナーはまだ判断していない。`TALK_STYLE` の1行で切り替えられる。
  3. **読み上げの間はマイクを閉じる**：「話す」を押すと、先に読み上げを止めてからマイクを開く。読み上げが始まったら、開いていたマイクも閉じる。ADR-0005 が参考にした「利用者が話し始めたら止める」は、「「話す」を押したら止める」に変わる。
  4. **認識した文の緊急の照合**：認識した文は入力欄に入り、「答える」で送るときに、文字入力と同じ語の照合（`web/src/flow/emergency.ts`、`training.ts` の回答の処理）を通る。Claude に送る前に照合することは変わらない（docs/phase2-decisions.md 項目10）。認識した時点では中断しない（誤認識を直せるようにするため。オーナーに確かめる）。
  5. **マイクが使えないとき**：音声認識の無いブラウザ、マイクの拒否、マイクが無いときは、ボタンを出さずに理由を文字で示し、文字入力で続ける。その回のうちは覚えておき、次の質問でも文字入力だけにする。声が無かった・通信の失敗は、知らせてもう一度押せるようにする。
  6. **読み上げる文**（`speech.ts`）：聞き取り係の文（固定文か、Workers の検査と監査役を通った Claude の文）、③確認の文、出来事の文、思い出せないときのその場の固定文。利用者の回答は使わない。返事を待つ間は読み上げない。
  7. **読み上げの中継**（`/api/tts`、`web/worker/tts.ts`）：
     - 受け取るのは `{ "text": "…" }` だけ（500字まで）。ほかの値が付いていたら拒否する。
     - ElevenLabs の `POST /v1/text-to-speech/{voice_id}` に、文とモデル `eleven_flash_v2_5`・`language_code: "ja"` だけを送る（出力は `mp3_44100_64`）。音声はためずにそのまま返し、事業者の見出し（履歴の ID など）は渡さない。`Cache-Control: no-store`。
     - キーと声の ID は secrets（`ELEVENLABS_API_KEY`・`ELEVENLABS_VOICE_ID`）にだけ置く。声の ID は英数字だけを通す。
     - 手元（localhost・127.0.0.1）からの呼び出しだけを通す。`/api/turn` の公開の切り替え（`PUBLIC_TURN`）では開かない。
     - モデル：ADR-0005 の表の Flash v2.5 を使う。2026-11-04 に ElevenLabs のモデルの一覧で、現行（廃止予定でない）で、日本語を含む言語に対応すると確かめた。後継の `eleven_v4_turbo` は、この呼び出し口で使えるかを一次資料で確かめられなかったので使わない。
  8. **ブラウザの読み上げへの切り替え**（`speaker.ts`）：中継の失敗、音声の再生の失敗、または **5秒** たっても再生が始まらないときは、ブラウザの読み上げ（`speechSynthesis`、日本語の声）に切り替え、その回の残りでは ElevenLabs を呼ばない。ブラウザの読み上げも無ければ、文の表示だけで進む。
     - 5秒の理由（Claude Code の提案）：Flash v2.5 の公称の遅延は約100ミリ秒で、Workers の中継と、音声をまとめて受け取る分を足しても、ふつうは数秒以内に始まる見込み。5秒を過ぎるのは事業者か通信の不調とみなす。短くすると、通信が少し遅いだけで声が途中で変わる回が増える。長くすると、利用者が無音で待つ。待つ間も画面には文が出ている。
  9. **最初のタップまで再生しない**：利用者がそのページで一度も操作していなければ、音声を取りに行かず、「読み上げを聞く」を出す。ブラウザが自動再生を止めたときも同じにし、事業者の失敗とはみなさない（切り替えない）。
  10. **そのほか**：同じ文の音声は、その回のあいだブラウザのメモリの中だけで使い回す（固定の質問を取り直さない）。保存しない。「読み上げを止める」「もう一度聞く」を置く。対話の画面を離れる（中断の画面・振り返り）と、読み上げとマイクを止める。中断の画面（`Stopped.tsx`）でも、残っていたものを止める（ADR-0011）。
  11. **聞き取り係の見せ方**：Listener に `mode`、`activity`（返事を待つ間は `thinking`、マイクが開いている間は `listening`、声が出ている間は `speaking`、ほかは `idle`）、`relief`（係の交代の後）を渡す。3D のパペット（#37、ADR-0032）がこの値で動く。3D の対話モードでは、返事を待つ間も聞き取り係を `thinking` で出す。`speaking` は声が実際に出ている間だけで、音声を取りに行っている間・読み上げが使えないとき・自動再生を止められたときは `idle` にする。ADR-0032 の「音声が無いときは文を表示している間、口を動かす」は、`activity` が `speaking` にならない場面のことなので、その場面で口を動かすかは 3D の側（Listener）が決める。
  12. **ログ**：画面は切り替えの種類（`tts: fallback_failed` など）だけ、Workers は失敗の種類（`tts: no_api_key`、`tts: upstream_502` など）だけを出す。ElevenLabs がエラーを返したときは、そのエラーの符号（`detail.status`。英小文字・数字・下線の64字まで）だけを足す（例：`tts: upstream_400:invalid_api_key`）。説明の文と本文は出さない。本文・音声・キーは、公開する版でも手元でも出さない（ADR-0007）。
- 外部事業者に送るもの（2026-11-04 に一次資料で確かめた。出典は README「外部事業者に送るもの」）：
  - 音声認識：ブラウザが使うサービスへ、利用者の声を送る。MDN は、Chrome などでは音声が認識のために Web サービスへ送られると書いている。Microsoft Edge は Azure Cognitive Services へ送り、録音は保存しないと公表している。Safari は Apple へ送られ、「Siri と音声入力の改善」に同意していなければ音声を保存しないと公表している（Safari のページの音声認識に当てはまるかは未確認）。Google Chrome の送信先と保持方針は、Google の一次資料で確かめられなかった（未確認）。Chrome 139 以降は端末内での認識も選べるが、日本語で使えるかは未確認で、今回は使っていない。
  - ElevenLabs：読み上げる文だけ。ElevenLabs は、生成した音声と文を既定で履歴に残す（ゼロ保持は Enterprise のみ。`enable_logging=false` も Enterprise のみ）。入出力をモデルの学習に使い、アカウントの設定で断れる（断った後の学習にだけ効く）。データは米国に移して保存する。
  - 聞き取り係の文に、語の照合で見つけられない形で利用者の言葉の言い直しが残っていれば、その部分は ElevenLabs にも届く（ADR-0030 の監査役と同じ）。
- 理由：
  - 押して話す：オーナーが選んだ選択肢の説明のとおり。自分の声と周りの会話を拾わず、1問ずつ直してから送る流れに合う。常に聞く作りより、マイクが開いている時間が短く、送る声も少ない。
  - 声を mode で決める：動きを減らす設定の人や、WebGL が使えない端末の人も、3D の対話モードを選べば声で練習できる（オーナーの選択肢の説明）。
  - 中継を手元だけにする：ElevenLabs は文字数で課金される。回数の制限と支出の上限が無いまま公開すると、誰でも呼べるお金のかかる口になる。
  - 認識した時点で中断しない：音声認識は誤変換をする（safety-test-plan E7 の「胸が来るしい」）。送る前に文字入力と同じ照合を通るので、Claude に届く前に中断できる。
- 却下案：
  - マイクを常に開き、話し始めたら読み上げを止める（ADR-0005 が参考にした設計。オーナーが押して話すを選んだ）。
  - ブラウザから ElevenLabs を直接呼ぶ（キーがブラウザに出る）。
  - 読み上げる文を URL に入れて GET で取る（URL はログに残りうる。privacy.md）。
  - `enable_logging=false` で ElevenLabs の履歴を残さない（Enterprise のみ）。
  - 音声を少しずつ受け取りながら再生する（MediaSource が要り、作りが大きくなる。文が短いので、まとめて受け取っても遅れは小さい見込み）。
  - 端末内の音声認識（`processLocally`）を使う（日本語で使えるかが未確認。次の候補として残す）。
- 確かめたこと（2026-11-04。Claude desktop のブラウザ画面、Chromium 152、開発用サーバーと `wrangler dev`）：
  - 作業コピーに ElevenLabs のキーが無い状態で `?mode=3d` を通し、`/api/tts` が 503 を返すとブラウザの読み上げ（Windows の日本語の声）に切り替わり、その回の残りでは `/api/tts` を呼ばなかった。コンソールに出たのは `tts: fallback_failed` だけだった。
  - ブラウザ画面はマイクを使えないので、「押して話す」はマイクの拒否になり、ボタンが消えて「文字で答えてください」が出て、文字入力で次の質問へ進んだ。次の質問でも文字入力だけだった。
  - ページの中で音声認識を偽物に替え、「押す → 入力欄に入る → 直す → 送る」が画面でつながり、押した時点で読み上げが止まってからマイクが開くことを確かめた。
  - 読み上げ中に体調の訴え（試験用の文）を送ると、中断の画面に移り、読み上げが止まった。2D モードでは、押して話す・読み上げ・`/api/tts` を使わなかった。幅375pxで横にはみ出さなかった。
  - その後、オーナーが作業コピーにキーを置いた状態で `/api/tts` を4回呼ぶと、ElevenLabs はどれも 400 を返し、エラーの符号は `api_key_id_used_as_api_key` だった（キーの欄に、API キーそのものではなく、キーの ID が入っている）。画面はブラウザの読み上げに切り替わる。符号を見るために、上の12のログを足した。
  - 未確認：ElevenLabs の本物の音声と、読み上げが始まるまでの待ち時間（キーを直した後に測る）。本物のマイクと声での「押して話す → 直す → 送る」（オーナーの手元の Chrome などで確かめる）。
