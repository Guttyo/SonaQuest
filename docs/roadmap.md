# 提出後の課題（roadmap）

**ここに書いたものは、提出版の実装には含まない。** どれも、作ると決めたものでも、時期を決めたものでもない。提出の後に検討する方向と、そのときに答えを出す問いを置いておく場所。取り組むかどうか、どの順に取り組むかはオーナーが決める。

- 提出までに行う作業は `docs/STATUS.md` の「未着手」と、GitHub の Issue で扱う。ここには移さない。
- 項目ごとに出所を書く。「オーナーの発言」はオーナーがチャットで言ったこと、「Claude Code の整理」と「外部の助言」は候補で、オーナーはまだ判断していない。
- 新しい項目を足すときも、出所を書く。範囲外の機能を作る判断は、ここではなく ADR（`docs/decisions.md`）で行う（`.claude/rules/scope.md`）。

## 1. 実際の服薬状況を扱う版
- 方向：サービスとして公開（ローンチ）するときは、利用者が自分の実際の服薬状況を示せることが必要になる。提出版は薬の中身を架空の内容で答える（ADR-0009、ADR-0022）。実際の情報を扱う版は、別の ADR で条件を決めてから作る。
- 出所：オーナーの発言（2026-11-03、チャット。ADR-0009「今後の課題」）
- 答えを出す問い（Claude Code の整理。結論ではない）：
  - 服薬情報・病名は個人情報保護法の要配慮個人情報にあたりうる。取得と外部への送信について、本人の同意をどう取るか
  - 外部事業者（Anthropic など）の保持期間はどうなっていて、ゼロ保持などの契約は要るか（ADR-0006）
  - 保存しない方針（ADR-0007）を続けるか。続けないなら、保存の範囲・期間・削除の方法をどうするか
  - 薬の名前を含む入力に対しても、医療判断をしないことを保てているか（docs/safety-test-plan.md S1〜S10 の再点検）
  - 医療機器の規制にあたらないか
  - 実際の服薬状況を結果画面でどう示すか（原文のまま表示する方針、ADR-0009 必須事項5）

## 2. Claude に任せる範囲を広げる
- 方向：提出版は、聞く項目と順番を固定し、Claude は質問の言い回しと、受け止め・質問し直しの文を作り、5観点を判定する（ADR-0025 の A）。何を聞くかも Claude が会話から決める形（B）は、提出の後に検討する。
- 出所：Claude Code の整理（ADR-0025 の推奨に「B は提出後に検討する」と書いた）。オーナーは A を決定した（2026-11-03）。B を検討するかは未判断
- 答えを出す問い：
  - 固定の進行（ADR-0012）に戻すとき、Claude が決めた質問をどう対応づけるか
  - 5観点を漏れなく聞くことと、回答の枠（最大10回）を、Claude に任せてよいか
  - 検査（ADR-0025、docs/safety-test-plan.md S16〜S19）の範囲をどこまで広げるか

## 3. 訓練の後に、利用者が自分で持ち帰る
- 方向：保存しない方針（ADR-0007）を保ったまま、繰り返し振り返れるようにする。アプリには残さず、利用者が自分の端末に持ち帰る形だけを候補にする。
- 出所：外部の助言の提案（`docs/reviews/2026-11-03-fable-docs-advice.md`）。オーナーは未判断
- 候補（外部の助言から）：
  - 振り返りの画面で、手薄なところ・選んだ準備行動・いつやるかだけをコピーできるようにする（固定文と利用者の選択で組み立てる。架空の薬の回答は含めない）
  - 選んだ「いつやるか」を、カレンダーの予定のファイル（`.ics`）として端末に書き出す
  - 「次は○か月後にもう一度」という固定文の案内（通知やリマインダーは持たない）
- 答えを出す問い：
  - これは `.claude/rules/scope.md` の作らないもの（履歴、共有）にあたるか。あたるなら、スコープを変えるか
  - 持ち帰る文を固定文と利用者の選択だけで作り、Claude に要約・言い換えさせないことを、どう確かめるか（`.claude/rules/safety.md`）

## 4. 医療者の立場で確かめる訓練（C-01）
- 方向：薬剤師や医師の立場から、患者の服薬情報や状況を確認するトレーニング。患者向けの訓練（提出版）とは別の機能として扱う。
- 出所：オーナーの発言（2026-11-04、チャット。Issue #44、ADR-0031）
- 提出版での扱い：実装しない。はじめにの画面に「Coming soon／将来構想・提供時期未定」と分かる表示だけを置く（docs/PRD.md「Coming soon の表示の決まり」、A-14）。完成済み・開発着手済みとは見せない。
- 答えを出す問い（Claude Code の整理。結論ではない）：
  - 患者の回答を確かめる立場になるので、医療判断をしない決まり（`.claude/rules/safety.md`）をどう当てはめるか。正誤の判定や助言をしない訓練として成り立つか
  - 医療者向けの訓練として、誰（薬剤師会、医療機関など）に内容を確かめてもらうか
  - 患者役を誰が演じるか（Claude に架空の患者を演じさせるなら、作ってよい文の範囲が ADR-0025 から大きく広がる）

## 6. 知識パックと、Claude に任せる範囲の段階（ADR-0040）
- 方向：質問バンク、出来事バンク、固定文カード（公的な仕組み・聞き取りの場面の事例。出典と確認日つき）、判定の基準、禁止表現を、コードから分けて版を付けられるデータにする。Claude はその解釈役で、任せる範囲は段階で広げる（段階1：固定文カードの選択、段階2：質問バンクからの追問の選択、段階3：やさしい日本語などへの言い直し）。
- 出所：オーナーの発言（2026-11-05、チャット。「モデルが賢くなっていったときに、その進化が直接的に患者、使う人たちの利益になるようなもの」）と、Claude Code の整理（ADR-0040。オーナーは未判断）
- 答えを出す問い：
  - `content.ts`・`prompt.ts`・`checks.ts` から切り出すときの形（JSON か TypeScript か）と、版の付け方
  - 段階1 のカードの選択を Claude の構造化出力に足すときの検査（選べるのはカードの ID だけにする）
  - 段階3 の言い直しを許すときの、検査（`checks.ts`）と監査役（ADR-0030）の作り直し

## 8. 医療者側の災害時の事務支援（将来構想の候補。要件 ID は付けない）
- 方向：災害時の薬の在庫管理・発注・納品、手書きの処方箋の整理、その後の請求事務の手間を減らす道具。平時と災害時で AI の使い方を分け、現場では紙と通信なしを前提にし、AI は通信が戻ったときの後処理（整理、転記、集計）に使う（ADR-0040 の決定4）。患者向けの訓練との接点は、5観点が救護所側で聞き取って記録する項目でもあること。
- 聞き取りで分かったこと（オーナーの発言、2026-11-05、チャット。ADR-0040 の背景）：いちばん効くのは、口頭の話を記録の形に整えること（患者と医療者の両方が確かめてから使う）。記録の項目は、薬の名前・量・処方元、飲めていない日数と残薬、アレルギー・副作用の経験に加え、注射・外用薬・貼付薬、毎日でない定期投与の薬、中断で体調を崩しやすい薬、医療用麻薬の有無。在庫の道具は、本部への定時の報告、他の拠点との共有、供給元の入荷見込み、需要の見込みを扱い、平時の供給不足の場面から同じものを使う。被災地では携帯が全くつながらない期間があり、報告や集計は通信のある離れた拠点で行われた。
- 本部のボードの試作（2026-11-05）：オーナーの頼みで、架空の救護所4か所と本部備蓄の模擬データ（患者の延べ人数、在庫と出庫のペース、入荷・融通の予定、紙の記録の届き方）で、地域本部のホワイトボードの代わりになるボードを、公開リポジトリの外（Artifact）に作った。提出版には含めない。採用・公開はオーナーの判断。
  - 似た仕組み（2026-11-05 に検索で確かめた範囲。一次資料で確かめ直す前）：EMIS は医療機関の被害・受け入れの状況、J-SPEED は救護所の診療実績（人数・症状）、eST-aid などは薬剤師会の安否・参集・施設の開閉と本部内の共有が中心で、救護所×品目の見込み日数と、紙の記録が本部に届いたかを1枚で見せる形は見つからなかった。eST-aid の救護所向け機能がいちばん近いので、新しさを言う前に確かめる。
- 聞き取りの道具（オーナーの発言、2026-11-05、チャット）：現場での聞き取りには、通信が無くても動くオフラインの AI の道具が要る。制作者が公開している別のアプリ SoapVox（端末内で動き、話した言葉を SOAP 形式の記録にまとめる）と構想が似ており、災害時の聞き取りの道具として似た構想を挙げてよい。SoapVox のコード・データ・プロンプトは複製しない（CLAUDE.md 絶対ルール1、ADR-0002 と同じ扱い）。
  - 答えを出す問い：端末内のモデルで、患者の口頭の話を記録の項目に振り分けられるか（薬の名前の修正や候補の提示はしない。患者と医療者の両方が確かめる）。通信が戻ったときに拠点の集計へどう渡すか。
- 出所：オーナーの発言（2026-11-05、チャット）。災害時の薬の入出庫と提供状況の把握は、近年の供給不足の場面とも共通する課題として挙げられた。どれも、公開する文書に書く前に一次資料で確かめる（下の問い）。提出版では実装せず、画面にも出さない（C-01 の Coming soon とは別で、表示も置かない）
- 答えを出す問い：
  - 対象（薬局か救護所か）と、誰が使うか。医療判断をしない決まり（`.claude/rules/safety.md`）をどう当てはめるか（在庫や請求の事務は医療判断ではないが、処方の内容に触れる）
  - 手書きの処方箋や記録を扱うとき、保存しない方針（ADR-0007）を続けられるか。続けないなら、要配慮個人情報の扱い（上の 1 と同じ問い）
  - 通信が無い間に紙で書いたものを、通信が戻ったときにどう取り込むか（写真、手入力、様式の統一）
  - 既存の仕組み（災害時の処方や請求の特例、薬剤師会の災害時の体制）との重なり。一次資料で確かめてから書く

## 11. 災害時の問診モード（C-05。将来構想）
- 方向：お薬の避難訓練を「訓練モード」と「災害時の問診モード」に分け、問診モードでは救護所の問診を訓練と同じ記録の項目で記録し、本部や診療所に薬剤需要の記録として残す。文字起こしは別のアプリ（制作者の既存のアプリ SoapVox）で行い、QR コードで記録の項目を渡す構想。
- 出所：オーナーの発言（2026-11-05、チャット）。提出版では、架空データのボード（B-04）と振り返りの記録の形（B-05）までを入れ、問診モード本体は押せない表示だけにした（ADR-0042）。
- 答えを出す問い：
  - 実際の患者の情報（名前、服薬、処方）を扱うので、「会話本文を保存しない」（絶対ルール3）、「発言を要約しない・医療判断をしない」（絶対ルール2、ADR-0025）、「架空の内容だけで練習する」（ADR-0009）を、問診モードに限ってどう変えるか。上の 1 の問い（同意、保持、医療機器の規制）と同じ
  - 「医師の処方」を記録に残すとき、アプリが処方に触れないことをどう保つか（人が入力する欄に限る）
  - 文字起こしの結果を QR で渡すとき、何を渡し何を渡さないか（本文か、項目に整えた値か）。通信が無い現場で動くか
  - J-SPEED の患者数と、このボードの患者数を同じ数字にすべきか（現場の判断）
- 本部のボードの次の形（Issue #101 の後。将来構想の候補）：
  - 実際の地図（外部の地図タイル）の上での経路の図示。災害時は通れる道路が限られ、どの経路が使えるかの共有が届け方の判断に要る（オーナーの発言、2026-11-05）。提出版は、架空の町の模式図（SVG。拠点と経路の状態、不足の印。Issue #105、ADR-0042 の追記）まで。地図のタイルは外部への送信と依存が要るので、ADR で決めてから。
  - 実データの入力・保存・送信、処方の連携、配送の確定（提案 → 承認・引当 → 出発 → 受領の操作）。提出版は架空データの表示と、メモリだけのデモ（架空の問診の入力、デモ時計。Issue #102、ADR-0043）まで。
  - 救護所と本部を別の画面で開き、救護所で確定した需要（未交付の数と必要時刻）だけを本部に渡す形。音声・文字起こしの本文・患者名は救護所の側に留める。

## 12. レセプト請求のための情報のエクスポート（検討中・未実装）
- 方向：災害時の救護所で記録した診療と処方の情報を、通信が戻った後のレセプト請求（診療報酬の請求）の事務に使える形で書き出す。上の 8（医療者側の災害時の事務支援）のうち、請求事務の手間を減らす部分にあたる。提出版のボードは架空データの表示とメモリだけのデモで、書き出しの機能は無い。
- 出所：オーナーの発言（2026-11-06、チャット。Issue #123。「あとでレセプト請求のための情報をエクスポートできるような仕組みも構築検討中ということにしておこう」）。作ると決めたものではない
- 答えを出す問い（Claude Code の整理。結論ではない）：
  - 処方・病名・氏名は要配慮個人情報にあたりうる。書き出す情報の範囲、本人の同意、書き出した先での扱いをどうするか（上の 1 と同じ問い）
  - 保存しない方針（ADR-0007、絶対ルール3）との関係。書き出すには記録を残す必要があり、実際の患者の情報を扱う版（上の 1・11）を先に決める必要がある
  - 医療判断の境界：請求の事務は医療判断ではないが、処方の内容に触れる（上の 8 と同じ）。アプリが病名や算定の内容を補ったり推定したりしないことを、どう保つか
  - 災害時の請求の特例や、既存のレセプトの仕組み（様式・電子請求）との重なり。一次資料で確かめてから書く
  - 誰が、どの拠点で、いつ書き出すか（救護所か本部か、通信が戻った後か）

## 13. 薬剤の需要の見込みを Claude で説明する（将来構想）
- 方向：ボードの在庫と需要の数字（今は在庫の算数で出している。ADR-0043 の追記）を、本部の担当者が読みやすいように Claude が文で説明する。需要の数そのものは Claude に作らせず、算数で出した数の説明だけにとどめる。
- 出所：オーナーの決定（2026-11-06、チャット。Issue #121・#123）。ボードで Claude に作らせる文は薬剤以外の連絡文だけにし、カルテの要約・需要の予測は作らない（将来構想にする）。作ると決めたものではない
- 答えを出す問い（Claude Code の整理。結論ではない）：
  - ADR-0043 の追記10（2026-11-05 オーナー決定）で「状況を解釈する文を画面に出さない」と決めた。需要の説明はこれにあたるので、新しい ADR とオーナーの決定が要る
  - 説明の文は品目に触れる。薬剤以外の連絡文だけにする決まり（2026-11-06）と、Claude の文の禁止表現（薬の名前・量への言及。`web/worker/checks.ts`、`.claude/rules/safety.md`）を、どう当てはめるか。品目名と数は Claude に作らせず、画面の固定の欄に出すだけにするか
  - 説明が予測や助言（「〜を多めに発注すべき」など）に見えないことを、検査と監査役（ADR-0030）でどう確かめるか
  - 実データを扱うなら、Claude に送る在庫・需要の情報の範囲と、外部事業者の保持（ADR-0006）。要配慮個人情報（上の 1）を送らない形にできるか
  - 医療機器の規制や、医薬品の供給の判断を支援する道具としての位置づけ（上の 1 と同じ問い）
