## 1. 使うモデル（ADR-0006）
| 選択肢 | 良い点 | 気になる点 |
|---|---|---|
| A. `claude-opus-5-5`（Claude Opus 5.5） | いちばん能力が高い Opus。effort（考える深さ）を `low` にすれば速さと費用を抑えられる | 入力 $4・出力 $20（100万トークンあたり）。思考は止められず、effort で調整する（既定は `medium`） |
| B. `claude-sonnet-5-5`（Claude Sonnet 5.5） | 速さと能力のつり合いがよい。入力 $2・出力 $10 | effort の既定は `high`。速さを優先するなら `low` にする |
| C. `claude-haiku-5-5`（Claude Haiku 5.5） | いちばん速く安い。入力 $0.10・出力 $0.50 | 曖昧な回答の読み取りや判定の一致率は、比べてみないと分からない |
| D. `claude-fable-5-1`（Claude Fable 5.1） | もっとも能力が高い | 入力 $10・出力 $50。1回の応答が長くなりうる。30日の保持が必要で、ゼロ保持の対象外 |

- 推奨：**A を effort `low` で始め、比較実験（docs/evidence.md）で B・C と比べてから確定**。参照資料は「安いモデルに替える前に、能力の高いモデルの effort を下げたものと比べる」ことを勧めている。1ターンの応答の速さ（音声にするなら特に）と判定の一致率で決める

## 2. 出力の形（ADR-0015）
| 選択肢 | 良い点 | 気になる点 |
|---|---|---|
| A. 構造化出力（`output_config.format` に JSON スキーマ）。観点の3段階、次の質問のID、`emergency`、③確認の分類の候補だけを返させる | 返る形がスキーマで決まる。Workers の検証（ADR-0015）が簡単。自由文が無いので、薬の名前の候補などが画面に出る経路が無い | 聞き返しの文面は固定文から選ぶことになる（項目3） |
| B. ツール呼び出し（`strict: true`）で同じ形を返させる | A と同じく形が決まる | 現行のモデルでは、特定のツールを必ず呼ばせる指定（`tool_choice` の `any`・`tool`）が 400 になる。A のほうが素直 |
| C. 自由文の応答から JSON を取り出す | 作るのが早い | 形が崩れうる。検証と安全の検査が重くなる |

- 推奨：**A**。旧式の `output_format` は使わない。温度などの指定（`temperature` 等）は 2026-10-21 以降 400 になるので送らない

## 3. 聞き返しの文面
| 選択肢 | 良い点 | 気になる点 |

## 5. プロンプトで禁じること（safety.md、ADR-0021・0022）

## 9. 失敗・時間切れ・検証の失敗（ADR-0012・0015）
- 推奨：Claude の応答を一定時間（例：8秒）待ち、失敗・時間切れ・検証の失敗のどれでも、**その回の残りを固定の質問の進行に切り替える**。それまでの回答と進行は失わない。判定できなかった観点は「判定できませんでした」
- 応答が `refusal`（安全の判定で断られた）のときも同じ扱いにする。参照資料は、Opus 5.5・Sonnet 5.5 では応答を断られたときに別のモデルで答え直す設定（`fallbacks: "default"` と専用の beta ヘッダー）を勧めている。使うかを決める
- SDK は失敗時に自動で2回まで再試行する。待ち時間の合計が延びるので、再試行の回数も決める

## 11. ログとデータの保持（ADR-0007、ADR-0006）
- Workers：Workers Logs は無効のまま。本文を `console.log` に出さない。出すのは件数・所要時間・エラーの種類だけ。実装の後に safety-test-plan P1（`wrangler tail` で本文が出ないこと）を確かめる

- 推奨：提出版はゼロ保持の契約なしで進め、初回画面と README に保持方針を書く（架空の内容で答える方針と合わせて）
