## つまずいたことと教訓
- **自動モードでは、ルールと hook の書き換えが止まった。** 自分の権限を広げる変更（マーカーを解除できる、push と PR を承認済みとみなせる）は、自動モードの安全判定に「自己改変」として止められた。CLAUDE.md の編集だけは通ってしまったが、同じ性質なので元に戻した。オーナーが「編集ごとに承認する」を選び、権限モードを毎回確認するものに切り替えてから進めた。次に同じ種類の作業をするときは、最初から編集ごとの承認で進める。
- **「main を見る」を守りにすると、ローカルの main を動かす操作すべてが抜け道になる。** 1回目の版は `git show main:<ファイル>` を見たので、`git tag main` や `git branch -f main` で作業ブランチを main に見せかけられた。2回目のレビューでも、`git push . HEAD:heads/main`、`-fBmain`、`rebase <起点> main` などが見つかった。次に「手元の参照を信じる」設計をするときは、その参照を動かせるコマンドを先に洗い出し、hook で止めきれない分を ADR に書いてから実装する。
- **止める範囲を広げると、ふだんの操作まで止める。** main を動かす操作を止めるとき、引数のどこかに main があれば止める書き方にしたため、`git switch -C feat/x main` や `git tag v0.1.0 main` まで止まった（2回目のレビュー）。作る・動かす参照の名前だけを見るように直した。止める試験と一緒に、止めてはいけない試験を必ず書く。
- **ファイル全体を読む判定は、多くのファイルを含むコミットで遅い。** 2回目のレビューの計測では、ファイルごとに `git show` を2回呼ぶ版は、ファイル数が多いと Bash の時間切れ（2分）に届くとされた。差分でマーカーの行が消えたファイルと、削除・名前の変更だけを全体で読むように直した。
